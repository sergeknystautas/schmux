# Flights

## What it does

A flight is the durable record of a manually advanced unit of work: a backlog item becomes one workspace, a planner session, an executor session, one or more reviewer sessions, and a commit session, in that order, only when the user moves the workflow forward (`backlog → planning → executing → reviewing → completing`). Completing is the last phase: the commit is ready, and the flight stays there, owning its workspace and sessions, until the user rebases, pushes, merges, and disposes it. A persistent pilot session supervises the working session of each phase; the monitor classifies completed working-session responses through Jev and notifies the pilot of interesting or uncertain planner turns and of every executor, reviewer, and committer turn. Two shared subsystems back it — a destructive-cleanup service and a local-target spawn launcher — so destructive disposal and the local spawn path are not private to flights.

## Pilot and monitor

Takeoff is available only from backlog. Once workspace assignment moves the flight
to planning, takeoff cannot be repeated, even after a spawn failure or loss of a
session or workspace. Partial outcomes remain visible. Pilot spawn success is
persisted before attempting the planner. The pilot model is flight-manager
configuration, not part of a flight: `flight_pilot.target`, set in Settings >
Flights > Pilot Supervision and read at each takeoff. Flights never carry a
pilot model and there is no fallback to the planner model. When it is unset or
not chat-capable, takeoff returns 409 before allocating a workspace or spawning
a session. Pilot chatter does not replace planner/executor activity in the
flight list.

Classification waits for the harness to complete a planner turn, then sends all
top-level assistant response text from that turn, in order. Tool output, thinking,
and child-agent responses are excluded. Codex completion summaries can omit earlier
response blocks, so the monitor retains those blocks from the turn's records.
Pending pilot guidance rechecks planner availability and both sessions' workspace
membership at delivery, including after an explicit retry.

Restarting the pilot or planner from the dashboard (`POST /api/sessions/{id}/restart`)
disposes the old session and spawns a replacement seeded from the same conversation
record. The flight follows: the assignment moves to the new session ID, the replaced
ID joins `prior_session_ids`, and retained turns and messages are re-pointed so the
subscription resumes after the retained cursor, pending deliveries reach the
replacement, and pilot decisions still validate. The seeded turns are not
classified again. Ingestion errors (`monitor: session <id>: …`) are recorded once
per distinct error, not on every recovery tick, and clear when that session's
subscription succeeds or the session is replaced.

Planner ingestion and classification run separately. Pending turns survive restart
and explicit retry appends a new attempt using the classifier definitions of the
running build. Notifications
retain source session/record ranges, the response, saved question/choice definitions,
confidence, the turn's spec/plan report and its check, and durable conversation path. The history exposes those
definitions even after a later schmux build changes them. Delivery is persisted before sending; a send
interrupted by daemon shutdown becomes `unknown` and cannot be blindly retried.
Queued outcomes are reconciled against the recipient runtime during monitor
reconciliation (including the 30-second recovery tick). Accepted notifications are
deduplicated by source turn and are not resent on recovery. Invalid retained IDs,
source references, or statuses make snapshot loading fail without rewriting it.

The direct Jev request uses keyed question and criterion objects, preserving YAML
choice order. The TypeSafe API key comes only from configured provider secrets
and is never saved with evidence. Live classifier accuracy and the live pilot round trip require manual
acceptance; fake-server tests establish transport and recovery behavior only.

The flight starts one persistent **pilot** chat session in the planner's workspace. The daemon delivers interesting or uncertain classifications to that chat. The pilot's final response is one JSON decision carrying exactly one of three forms: guidance (`{"to":"planner","guidance":"Check the spec."}`), a request for the next reviewer (`{"next_reviewer":"…"}`, see "Supervising review"), or a stop (`{"stop":"…"}`, see "Pilot stop"). The pilot does not copy a notification ID; a `notification_id` field from a pilot prompted by an earlier build is accepted and ignored. Every message schmux sends the pilot (a notification or a launch notice) restates the decision contract (`decisionContract`, `internal/flights/prompts.go`), so a pilot whose takeoff prompt came from an earlier build follows the current rules without being restarted. `to` names the recipient's role and is required whenever guidance is a string; `next_reviewer` and `stop` take no `to`. `to` may name any working role whose session the flight has started (`planner`, `executor`, `reviewer`, `commit`): every started session stays addressable in every later phase, so the pilot can send the planner back to its plan during execution or ask the executor a question during review. The daemon resolves the role to the currently assigned session, and a response cannot name a session ID. A null guidance value leaves everyone alone, and any `to` with it is ignored. More than one form, malformed JSON, unknown fields, blank text, and a missing, unknown, or not-yet-started `to` produce visible decision errors (the error names the roles the flight has started) and never trigger delivery or a spawn. There is no default recipient. The pilot is the flight's orchestrator: every completed pilot response is read for a decision, whatever prompted it (a notification, the execution or review notice, or the user), and schmux does not track which message a turn answered. A response that is not a JSON object (a code fence around one is stripped) is the pilot talking to the user; it is retained as `skipped`, not parsed, and sends nothing, and it is not an error. A decision that cannot be applied is recorded on the pilot's turn as a visible error and sends nothing to anyone; schmux does not send the pilot a rejection to answer again (that loop was removed on 2026-10-28, see "Architecture decisions"). The user sees the error on the flight's story and can retry the turn there once the cause is fixed; the pilot decides again whenever it has something to say.

The flight worker subscribes to the pilot's chat and to every started working session's chat (`monitoredSessions`): the planner, the executor, the current reviewer, and the committer, each from the phase that starts it until the flight leaves `completing`. The pilot orchestrates all of them, so the monitor follows all of them; which turns wake the pilot is decided per turn (see below). The reviewer that was current when the user entered completion is recorded on the completion operation as a `reviewer` resource, as history. Only working-session responses go to Jev. Completed pilot responses are retained and interpreted inside the daemon; there is no CLI command or HTTP return endpoint. The worker checks current pilot and recipient assignment, workspace membership, and recipient availability. It persists guidance before calling the recipient's chat runtime directly. Guidance still pending when the phase changes keeps its recipient while that session still holds its role. The recipient sees `[Pilot]` attribution; retained evidence keeps the exact unprefixed text, source pilot turn, and delivery outcome. Pilot turns use `skipped` because they are not classified by Jev. Replaying a pilot response deduplicates its message by source session and turn boundary. Unknown crash-time delivery is never blindly resent. Native questions and permissions remain manual.

The monitor subscribes to the planner's chat runtime (via `Runtime.Subscribe`), extracts the full response of each completed turn (Claude `result` or Codex `turn/completed`), and sends it directly to the Jev HTTP API. The schema and routing rules are part of the workflow and live in schmux itself, in `internal/flights/flight-monitor.yaml`, embedded in the binary. Every installation asks the same questions; nothing is installed into or read from `~/.schmux`, and users do not edit them. The definitions must include the `planner`, `executor`, `reviewer`, and `commit` roles; validation names a missing role (`flight-monitor: role "reviewer" is required`), and a test keeps the shipped file valid. The definitions are, for the planner, `attention` (needs attention vs routine) and `planning_artifacts` (which planning documents the response claims are written); for the executor, `attention` and `execution_state` (finished, stopped, or still working); for the reviewer, `review_state` (finished, fixing, blocked), `tests` (run and passed, run and failed, not run), `test_rules_review` (compliant, violations, not run), `changed_work` (changed, unchanged), and `artifacts_named` (named, incomplete); for the committer, `attention` and `completion_state` (committed, gate failed, working, blocked). A turn of the phase's own worker (the executor while executing, the reviewer while reviewing, the committer and the reviewer while completing) notifies the pilot on every turn, whatever the classifiers say; `execution_state` and every reviewer and committer classifier therefore have empty `notify_on` and exist to inform the pilot and the user. Every other followed turn (every planner turn, and an earlier phase's session the user is still talking to) wakes the pilot only when any answer's confidence falls below its `min_confidence` threshold or any answer's choice is in the classifier's `notify_on` list. Failed or interrupted turns notify the pilot with the harness outcome without asking Jev to infer it. A successful turn with no response text records `skipped`, never calls Jev, and does not notify, unless the daemon's own checks found a placement violation or the verified execution report in it.

### Supervising execution

**Enter execution** records `execution_started_at`, fixes the report target (the verified plan path with its extension replaced by `-execution.md`, or `review/<flight-id>-execution.md` when no plan was verified; a later planner report never moves it), spawns the executor with a prompt that tells it to run `superpowers:executing-plans`, use no subagents, create no worktrees, make no commits, skip `superpowers:finishing-a-development-branch`, follow the how-to-work rules (`executionDiscipline` in `internal/flights/prompts.go`: run each test once, rerun one only with the pilot's permission (asked by ending the turn), and never loop it; report a failing test rather than hunting flakiness, checking whether it predated the change, or changing the test to pass; start a long suite once and never restart, kill, sleep on, or poll it; never revert or discard changes unless a human asks; stop and report when a test fails or work is blocked), and write the report when finished, and queues an `execution_notice` for the pilot. The notice tells the pilot an executor has launched, names its session and the report path, and says guidance can now go to `executor`; it needs no decision. What to do with each executor turn arrives in that turn's notification: compare the work with the spec and plan, send the executor guidance about substantial drift, check the conversation for actual use of the execution skill, and do not implement, commit, edit the spec or plan, change the phase, dispose the flight, or wipe the workspace; the turn whose report verifies also tells the pilot that execution has finished and the user decides when to enter review.

While the flight is `executing`, every completed executor turn notifies the pilot, whatever the classifiers say: most executions end in one turn, and the pilot's comparison with the plan is the drift check. The planner does not check executed work (a fresh reviewer does); it stays assigned, the monitor keeps following it, its turns remain classifier-gated, and the pilot may still address it, for example to have the plan revised when the executor finds it wrong. A failed classification (no key, invalid YAML, Jev error) does not hold the notification back: it goes out with `Classification failed: <error>` in place of answers, and a later retry records its answers in monitor history only. Executor notifications add a **Skill check** (`executing-plans invoked at record N` from a Claude `Skill` tool call, `executing-plans skill file read at record N` from a Codex command that reads the skill file, or `executing-plans not found`; only the executor's records count) and a **Report check** (`not written yet`, `verified: <path>`, or the failure reason). The report counts only if it is a regular, nonempty file inside the workspace modified after execution started, so a file left from before does not; git-ignore is not checked. The first turn whose check passes sets `report_path` on the flight; a verified report is how the daemon knows execution has finished. No Jev answer or executor claim substitutes for it. The flight stays `executing` until the user clicks **Enter review**, which does not require a verified report. Supervision runs at turn boundaries only; it does not stop a commit or subagent as it happens, and questions and permissions stay human-answered.

The flight detail page shows the report target (marked not yet verified until `report_path` is set), the same activity line as the list, and each executor turn's skill and report checks. The activity line leads with a session waiting on a native question or permission over one with newer output.

### Supervising review

**Enter review** is offered on an `executing` flight; the daemon requires only a workspace and idle cleanup, and there is no confirmation. It records `review_started_at`, moves the flight to `reviewing`, spawns a fresh **reviewer** chat session with the planner's model (`planner_model`), and queues a `review_notice` for the pilot naming the reviewer; it needs no decision. The reviewer has no history from the planner, the executor, or an earlier reviewer. Its prompt (`ReviewerPrompt`, `internal/flights/prompts.go`) tells it to review the work as the plan's author would and fix every problem in place without starting over; check reuse, the repository's patterns and style or review skills, docs, and tests that test behavior; verify every acceptance criterion in the spec with evidence; run the repository's own tests and checks and rerun them after its last change; run the `test-rules-review` skill until clean; put the artifacts the acceptance criteria name under `review/` and write a self-contained HTML account at `review/<plan file stem>-review.html` in the workspace; and end by saying whether it changed anything and listing the summary and artifacts, without committing, pushing, rebasing, finalizing, or changing the phase. It carries the executor's how-to-work rules and the `[Pilot]` note, and names the spec, plan, and verified report (or says no verified report exists). The planning steps now include writing an **Acceptance criteria** section in the spec before the coherence check, so the reviewer has criteria to verify; schmux never reads that section.

While the flight is `reviewing`, every completed reviewer turn notifies the pilot with the reviewer classifiers' answers and a **Skill check** (`test-rules-review invoked at record N`, `test-rules-review skill file read at record N`, or `test-rules-review not found`; only the reviewer's own records count). The notification carries the pilot's review job: hold the reviewer to its prompt, look in the reviewer's conversation for the test commands actually run after the last change and the skill actually invoked rather than trusting its claim, send guidance with `"to": "reviewer"`, ask for the next reviewer when this one changed something, and record a stop if the chain has gone off the rails.

When a reviewer reports it changed something, the pilot sends `next_reviewer`: a paragraph saying what the last reviewer changed and what to re-check. The daemon records a `next_review` operation, spawns a fresh reviewer whose prompt is the reviewer prompt plus that paragraph (it reviews the whole change again, not only the fix), moves the `reviewer` assignment to it with the previous session ID in `prior_session_ids`, records the paragraph as a `next_reviewer` message, and queues another `review_notice`. The superseded reviewer keeps running; nothing is sent to it or done to it. The review has converged when a reviewer reports it changed nothing and everything it checked passed; the pilot then sends no `next_reviewer`. Nothing caps the chain: a chain that does not converge is the pilot's to report with a stop.

The flight list and detail page show the latest reviewer classification in words ("Reviewer reports: finished, tests run and passed, test-rules-review compliant, changed nothing, artifacts named"), derived from the retained monitor turns as `review_status`. Superseded reviewers count: after a `next_reviewer`, the previous reviewer's reading stays until the new reviewer has a classified turn. Each classifier has its own words, so `not_run` reads "tests not run" or "test-rules-review not run". Both pages also show the pilot's latest delivered or queued guidance ("Pilot to Reviewer: …", `pilot_guidance`) in its own line; monitor history keeps every message. The detail page lists the current and prior reviewer sessions among the resources. Schmux does not run the tests, read the spec, plan, report, or test files, check whether the summary or any artifact exists, link the summary, or block a transition on any classification; the reviewer's chat already rewrites workspace paths to the dashboard's viewer. Acceptance criteria name the repository's functional tests and checks, not workflow-owned steps; `test-rules-review`, review summaries, commit, finalize, and rebase belong to review or completion, and the generated plan ends with implementation and the execution report.

### Pilot stop

In any supervised phase, the pilot may decide `stop` with a reason. The daemon records `pilot_stop` on the flight (phase, reason, source turn, time) and a `pilot_stop` message in monitor history, and does nothing else: no chat message, cancellation, interruption, hidden control, or disabled action. Sessions keep running, later turns keep notifying, and every phase action stays offered. The list's activity line and the detail page lead with "Pilot stopped: <reason>" until the phase changes; the payload exposes `pilot_stop` only while the flight is in the phase the stop was made in. The user reads the reason and decides.

### Completion

**Enter completion** is offered on a `reviewing` flight, whatever the reviewer reported, whether a summary exists, and whether a stop is recorded; an `executing` flight no longer offers it (the edit form's stage field remains the escape hatch). It spawns the **committer** with the executor's model under the `commit` role, records on the completion operation which reviewer was current (a `reviewer` resource), and moves the flight to `completing`. The committer's prompt (`CommitterPrompt`) says the user approved the work, then: stage every change except `review/`, including the spec and plan at their exact paths, and invoke the repository's commit skill, running its gates once per attempt; on a gate failure stop and report the actual output, without rerunning gates, changing the work, reverting, or starting or killing a suite; only after the work commit succeeds remove `review/`; run `/finalize --amend --commit <hash> --spec <spec_path> --plan <plan_path>`; amend the work commit with the finalize changes without rerunning gates; report the final hash and files; never rebase or push. The repository's `finalize` and `commit` skills (`.agents/skills/`) have an explicit amend mode for this: finalize processes only the named documents, makes the standard consolidation choices without asking, and amends the named commit through `/commit --amend`, which keeps the message and skips the gates.

While the flight is `completing`, every committer turn notifies the pilot with the `commit` classifiers' answers and the commit job: check the response against the workspace, route a gate failure to a fresh reviewer with `next_reviewer` carrying the failure, and let the committer retry only after a reviewer changes nothing and everything it checked passed. Guidance may go to any started session, `"to": "commit"` or `"to": "reviewer"` in practice. The assigned reviewer is followed and notifies on every turn while completing, whether it reviewed the work before completion or was started after a gate failed. Nothing is terminated or unstaged by the daemon. Completing is the last phase; nothing follows it but dispose. Rebase, push, and merge are the user's.

Configure flight naming and the TypeSafe API key under **Settings → Flights**.
The Flights page's **Settings** link opens this tab. The key is in **Pilot Supervision**.
Set, update, and removal use the standard password prompt and config-update API;
only the presence of a stored key is returned to the browser. The key is saved in
`secrets.json` under `providers.typesafe.TYPESAFE_API_KEY`, using the same owner-only,
atomic secret-file storage as other providers. It is read for each classification,
so changes apply without restarting the daemon. Removing the stored key leaves
classification unconfigured. Existing failed turns can be retried from monitor history.
A missing key is a visible classification failure, not a routine ruling. Neither
Claude nor the TypeSafe Claude skill sits in the production classification path.

The Flights page displays a warning above the list and forms when the daemon
cannot resolve the TypeSafe API key. The warning
links to the Flights settings tab. This check comes from GET `/api/config`
and uses the same configured provider secret as classification.
The local readiness check does not call Jev or verify the key with the provider.

## Architecture decisions

- **Sole-writer rule.** `flights.Manager` is the only writer of `~/.schmux/flights.json`. Handlers, transition functions, and the persistence layer never edit flight state directly — they call into the manager and serialize the resulting snapshot atomically (`internal/flights/manager.go:108`). A pending `Operation` is persisted before any external call, then re-persisted with its outcome, so a daemon crash leaves a visible attempt.
- **Manual workflow.** No session signal, chat activity, transcript assessment, or elapsed time advances a flight. The user explicitly clicks each arrow. The `Spec:`/`Plan:` report is information for the executor's and reviewer's prompts, never a gate: Enter execution does not require a verified report and rechecks nothing (an earlier build returned 409 without one; the user rejected that on 2026-10-25 and again on 2026-10-28: parsing to retrieve information is in line with the approach, blocking the user on it is not). Schmux never inspects planning quality. Execution supervision records skill use and report evidence for the pilot and the user, but a verified report or a classifier answer never advances the flight.
- **The skills choose where the spec and plan go.** Schmux never dictates a location. It tells the planner to let `superpowers:brainstorming` and `superpowers:writing-plans` place the documents and to report the absolute paths, then deterministically checks each report and surfaces any violation in the monitor history and the pilot's notification.
- **One pilot supervises every working role.** There is no second pilot. `monitoredSessions` (`internal/flights/monitor.go`) follows every session the flight has started, in every supervised phase, and a pilot decision may address any of them by role, never by session ID; the daemon resolves the role to the flight's currently assigned session, and a decision error is a visible error on the turn, nothing more. An earlier build followed and let the pilot address only the current phase's worker; it was removed on 2026-10-27 because an orchestrator must be able to reach, and hear from, every session it is responsible for (the planner during execution, the pre-completion reviewer during completion). Which turns wake the pilot is still decided per turn: the phase's own worker on every turn, everyone else through the classifiers.
- **Only the verified report proves execution finished.** A Jev answer, an `execution_state: finished` classification, and the executor's own claim are all not proof. The report counts only as a regular, nonempty file inside the workspace modified after execution started; the first turn whose check passes sets the flight's `report_path`.
- **Every executor turn notifies the pilot, whatever the classifiers say.** A failed classification still notifies, with the classification error in place of answers: most executions end in one turn, and a classifier that hid an ordinary-looking turn would leave the one turn most executions produce unwatched. `notify_on` and `min_confidence` decide the pilot's planning turns only.
- **A fresh reviewer, not the planner, reviews the work.** The planner's conversation is biased toward its own plan being right, so the planner does not check executed work and has no `work_check` classifier. Each reviewer starts with no shared history; after a reviewer changes anything, the pilot asks for another, and the chain converges when one changes nothing and everything it checked passed. The superseded reviewer is left running, untouched.
- **Review and completion read nothing from the workspace.** The daemon runs no tests, reads no spec, plan, report, or test file, checks no file's existence, and parses no structured line from a reviewer or committer response. The review reading is Jev's classification of the response, shown in words; the skill check reads only the session's own chat records. No classification, missing artifact, or pilot stop blocks Enter completion or dispose.
- **The pilot is an orchestrator, not a responder.** Every completed pilot response is read for a decision, whatever prompted it, and a decision is never tied to a notification. An earlier build read only responses to messages schmux had sent (first by a copied `notification_id`, then by the chat input the turn answered) and rejected the rest; it was removed because it blocked the pilot from acting on the user's instructions and stalled a flight when a `next_reviewer` named an executor notification during review. Prose is the pilot talking to the user and is not an error.
- **Schmux never answers the pilot back.** A decision error (wrong recipient, malformed JSON, a failed spawn) is recorded on the pilot's turn and shown on the flight; nothing is sent to the pilot. Builds before 2026-10-28 sent the error back as a `rejection` message so the pilot could "answer again", bounded to one per decision. The user asked for that retry loop to go on 2026-10-27, with the rest of the request/response design: schmux tells the pilot what happened and carries out its decisions, it does not negotiate with it. The `rejection` message kind stays loadable as history.
- **There is no done state.** Completing is the last phase. The stage-1 build had a "Mark done" button and a `done` state as a placeholder for the unbuilt rebase, push, and merge steps; the user never asked for them, and they were removed on 2026-10-28. A flight stays in `completing`, owning its workspace and sessions and still supervised, until the user disposes it. `loadSnapshot` maps a recorded `done` state to `completing`; a recorded `done` operation stays in history (`ActionDone` is valid but never written).
- **A stop records and shows; it does nothing else.** A pilot `stop` is a flight field and a monitor-history message. Nothing is cancelled, interrupted, hidden, or disabled; the user decides what to do.
- **Two independent state axes.** `WorkflowState` is the stage axis (`backlog`/`planning`/`executing`/`reviewing`/`completing`). `CleanupState` is the destructive-cleanup axis (`idle`/`disposing`). A `completing` workflow with `disposing` cleanup is valid and retryable. `requireIdle` rejects transitions while cleanup is in flight (`internal/flights/transitions.go:87`).
- **Workspace allocation belongs to takeoff.** A backlog takeoff calls `workspace.Manager.GetOrCreateWithLabel`. Planning does not offer takeoff again; a failed spawn or missing resource stays visible without respawning sessions or reallocating a workspace.
- **Per-flight op-lock, no global lock during external calls.** `flights.Manager.mu` is held only across in-memory edits and persistence. The slow `SpawnLocal` and `DisposeAll` calls run under a per-flight mutex from `opLocks`, so two transitions on the same flight never interleave while two transitions on different flights never contend.
- **One cleanup path.** `disposal.Service.DisposeAll` is the only place that sequences workspace disposal. Dashboard `dispose-all` and flight `dispose` both call it; neither holds its own copy. Force-purge semantics come from exposing `workspace.Manager.DisposeForcePurge` rather than reimplementing filesystem deletion. Remote refs are never modified.
- **One local spawn path.** `spawnlaunch.Launcher` validates the target, checks chat-capability, resolves fence, resolves persona/style context, calls `session.Manager.Spawn`, writes a spawn log, and broadcasts on success. The dashboard's multi-target `/api/spawn` handler and `flights.Manager.Takeoff`/`EnterExecution`/`EnterReview`/`EnterCompletion` and the next-reviewer spawn all use it.
- **Delimited original prompt.** The planner/executor prompts reproduce the original flight prompt byte-for-byte between `----- BEGIN/END ORIGINAL PROMPT -----` markers (`internal/flights/prompts.go:8`) so the flight operator can review the exact wording without diffing composited instructions.
- **No new event channel.** The existing `/ws/dashboard` payload gains a full `flights` array on its initial and debounced snapshots. Clients replace the array from every payload; they never poll. The detail route refetches after a reconnect broadcast that mentions its flight. The list's activity line reads `sessionsById` from the same `SessionsContext`; no polling, no second channel.
- **Dispose confirmation matches workspace ID.** `POST /api/flights/{flightID}/dispose` requires the body's `workspace_id` to match the flight's recorded workspace; a mismatch returns 409 and performs no cleanup. The dashboard consequence modal names the workspace and everything destruction will take (`FlightDisposeModal.tsx`). A flight with no workspace removes at once with a plain Remove confirm.
- **Dispose is the only removal.** Dispose is the sole removal action; there is no separate cancellation state or record-only deletion: the flight record always leaves the list when its resources do, or, when there are no resources, immediately. No path may orphan a workspace from its flight or vice versa; the dashboard's `DELETE /api/flights/{id}` route is unregistered for the same reason.
- **Daemon-generated names.** A flight's `short_name` is written only by the background namer (`internal/flights/naming.go`) through the `flight-name` oneshot (`internal/flightname`); create and update requests no longer carry it. Users never type a name, and creating or editing a flight never waits on the LLM. A flight with empty `name_prompt` is a placeholder — every flight that predates the namer, or was created while naming was off — and is named on the next pass once `flight_name.target` is set, so no migration code exists.
- **Rename on 5% drift from `name_prompt`, not from the last edit.** `promptChange(name_prompt, prompt) >= renameThreshold` (rune Levenshtein divided by the longer string). Comparing against the prompt the current name came from makes many small edits that add up to a real change still trigger a rename, while a typo fix never does.
- **Stale results are dropped, not merged.** The pass snapshots the prompt, calls the LLM outside every manager lock and the per-flight op-lock (so a takeoff never waits on naming), then writes only if the prompt still matches the snapshot. A changed prompt or a disposed flight discards the result; the next pass picks it up.
- **Naming failures live in `name_error`, not `Operations`.** Operations are workflow transitions and `LastError` is derived from them; mixing naming failures in would muddy both. Retries back off 1m → 1h per flight in memory only (`nextBackoff`); a success, a prompt change, or a daemon restart starts the backoff over. An identical repeated error does not rewrite `flights.json` or broadcast.
- **No model means naming is off, not an error.** An empty `flight_name.target` yields `ErrNamingOff`: no `name_error`, no backoff, the ID label stays. There is deliberately no fallback to `branch_suggest` targets. A configured target that doesn't resolve (`ErrTargetNotFound`) is a real failure and shows as `name_error`. A name the model returns that breaks a rule (empty, control characters, 10 or more words, over 80 characters) is `ErrInvalidName`; its `name_error` states the broken rule and quotes the rejected name. Names are not required to be unique.

## Design history

- **Two classifier questions over one combined ruling.** The `flight-monitor.yaml` definitions ship `attention` and `planning_artifacts` as separate Choice questions over the same planner turn. Each has its own `notify_on` and `min_confidence`, so a turn can require attention and still claim a planning artifact is ready without forcing the observations into one exclusive classification. The YAML choice order is preserved on every Jev request — feasibility runs found that reordering choices could change the model's answers.
- **Takeoff is one-shot by user decision.** A planning flight does not gain a second takeoff after a spawn failure, session loss, or workspace loss; partial outcomes remain visible. An earlier takeoff-retry feature was removed at the user's request because the supervisor flow already covers the recovery surface.
- **Deliberately excluded scope.** Permission answers and native questions stay human-answered; nothing schedules or auto-advances a phase. Execution supervision runs at turn boundaries only: it does not stop a commit or a subagent dispatch as it happens. Restarting execution, wiping the workspace, capturing a baseline, terminating or unstaging a failed committer, rebase, and push are not built. Pilot guidance is delivered as ordinary chat input and may queue behind a native permission card that the user must resolve manually.
- **The question set is part of the workflow, not user configuration.** The workflow is not something each user designs, so the classifier definitions ship inside schmux (`internal/flights/flight-monitor.yaml`, embedded) rather than being installed into `~/.schmux` for users to edit. An earlier build installed and read a per-user copy; that file is no longer read. Schemas and routing live in the file; the Go engine only knows Choice questions and `notify_on` semantics. Adding another Choice question of that shape needs no Go change.
- **Classification independence from agent harnesses.** The direct Jev HTTP request sits in `internal/flights/monitor_jev.go` with keyed question/criterion objects and bearer auth; Claude and the TypeSafe Claude skill are not in the production path. Classifier feasibility evidence came from an out-of-repo Jev spike against real final assistant messages; the live classifier's accuracy on the four backlog flights is pending manual acceptance, so unit tests prove transport and recovery, not accuracy.
- **The skill check can only be as strong as the harness allows.** Claude invokes a skill through a `Skill` tool call; Codex has no skill tool and reads `SKILL.md` with a shell command, recorded as a `commandExecution` item. For Codex the check can therefore only show that the skill file was read, and its text says which kind of evidence it found: `executing-plans invoked at record N`, `executing-plans skill file read at record N`, or `executing-plans not found`.
- **Forbidden behavior does happen, so supervision runs at turn boundaries only.** Of the 36 retained executions examined for the design, 1 ran `git commit` and 4 dispatched an `Agent`, and 28 ended in a single completed turn. Both numbers shaped the increment: the executor's prohibitions stay prompt instructions (only actual skill use is checked), and every executor turn notifies the pilot regardless of its classifiers.

## Gotchas

- **Snapshot failures disable flights, not the daemon.** Unreadable, malformed, or invalid snapshots (including unsupported historical states, roles, and actions) are logged. Flight endpoints return 503, while sessions and workspaces remain available. No manager is exposed for writes, and the original snapshot is never rewritten or repaired.

- **A flight's resources include any session in the workspace.** `dispose` enumerates sessions live in the workspace at call time, not only the planner/executor/commit assignments. Other sessions stored under the same workspace ID that belong to a different flight are left in place.
- **Chat history is deleted only by dispose.** Ordinary `dispose-all` keeps the conversation record (default retention). Dispose passes `ChatSessionIDs` (recorded current + prior IDs) plus live-workspace sessions into `disposal.Service`, which calls `chat.DeleteConversations` only when that list is non-empty.
- **Force-purge rejects on stuck sessions.** `disposal.Service` calls `Workspaces.DisposeForcePurge` only after every session dispose succeeds; otherwise it reverts the workspace status and returns the session errors joined. A live session is never left behind a purged workspace.
- **Workspace dispose-guard rails are bypassed by force-purge.** Uncommitted changes, unpushed commits, and recycling all lose to `DisposeForcePurge`. The flight branch is removed at the end via `Workspaces.CleanupFlightBranch` only when no other worktree still references it; remote refs are never touched.
- **Restart preserves the `disposing` state.** Daemon restart leaves cleanup-state and recorded outcomes intact; an incomplete dispose can be retried explicitly. Already-absent resources count as cleaned.
- **The flight edit form lets the user pick a non-listed value.** Every recorded field (including planner/executor models) is editable in every stage; a value that has since been removed from config stays selectable on the flight that recorded it (`FlightEditForm.tsx`).
- **Stage is editable directly.** Saving a new `workflow_state` does not run a transition; it only writes the field. To advance, click the action button.
- **Workspace header flight button is conditional.** It appears only when the current workspace appears in the derived `flightByWorkspaceId` map (recorded assignments, not lifecycle hints). Unassigned workspaces render no flight control — there is no "create flight for this workspace" button on the header.
- **`order` is meaningful only in backlog.** Section membership and manual ordering use `workflow_state`, including backlog flights that retain a workspace after editing. `POST /api/flights/order` requires every backlog ID and rejects flights in another workflow state. Started flights use session activity order.
- **Activity line uses the sidebar's adjusted timestamp rule.** The list ranks started flights by `last_output_at` minus one hour when the session is in progress, exactly as `lib/workspaceSort.ts:24` does for the sidebar workspace time sort. The shared `sessionActivityTime`/`latestActivityTime` helpers in `workspaceSort.ts` are the single source. `flightActivity` also records the in-progress result, and the line reads "Working" from it, so the wording and the order agree. A resolved session with no output yet still gets a linked line; "session gone" means no role session resolved at all.
- **One status line per started row.** The line combines the recorded stage, selected role, observed session state, and relative output time. Cleanup replaces it with "Disposing"; otherwise a pilot stop replaces it with "Pilot stopped: <reason>", and on the list a review reading replaces it with "Reviewer reports: …" (the detail page shows the reading in its own row); no assignments renders `<Stage> · No session`. In a tie on activity time the line names the role the current phase supervises. There are no list status pills or resource stacks. The flight name opens the resource inventory on the detail page. Section headers explain manual backlog order and the adjusted activity order.
- **Sapling workspace labels are fixed at takeoff.** Takeoff sets the workspace label from the flight's `short_name` at that moment (`internal/flights/transitions.go:230-233`, `displayName`). Git repos get branch `schmux/flight/<ID>` and no label. A later rename does not relabel a Sapling workspace; the dashboard surfaces the current name via `flightLabel` everywhere else.
- **`StartNaming` must run after `wireCallbacks`.** The oneshot path resolves targets through the model manager that `wireCallbacks` installs (`oneshot.SetModelManager`, `models.SetDefault`). Starting the namer earlier makes the first pass report every placeholder as "model not found"; `Run` starts it right after `wireCallbacks` (`internal/daemon/daemon.go:479`).
- **`short_name` in a request is silently ignored.** The flight handlers don't use `DisallowUnknownFields`, so an old client sending `short_name` gets a 200 and no change.
- **`name_error` shows only on the list rows and the detail page.** The workspace header button and toasts show `flightLabel` alone.
- **A waiting session is not "in progress", so the activity line needs its own rule.** A pending question or permission sets the chat session's nudge state to "Needs Input", which `isSessionInProgress` (`assets/dashboard/src/lib/workspaceSort.ts`) does not count as in progress. Without a flights-specific rule a waiting executor is hidden whenever the planner spoke more recently. `flightActivity` (`assets/dashboard/src/lib/flights.ts`) prefers a "Needs Input" session, and `useFlightInProgress` keeps the list and the detail page on one predicate. The shared in-progress check and the sidebar workspace sort are unchanged.
- **The executor's prohibitions are not enforced.** "No subagents, no commits, skip `superpowers:finishing-a-development-branch`" is prompt text. Only actual use of the execution skill is checked, and only at turn boundaries; nothing stops a commit or a subagent dispatch mid-turn.

## Common modification patterns

- **Add a new transition.** Add an `OperationAction` constant in `internal/flights/model.go`, a `(m *Manager) <Name>(ctx, id)` in `transitions.go`, a HTTP handler in `internal/dashboard/handlers_flights.go`, a route in `registerMutatingRoutes`, a typed client function in `assets/dashboard/src/lib/api.ts`, a button in `FlightActions.tsx`, and an `Action`→`label` mapping in `assets/dashboard/src/lib/flights.ts`. Persist a pending `Operation` before any external call, then its outcome.
- **Change a role's prompt.** Edit `internal/flights/prompts.go` — keep the `BEGIN ORIGINAL PROMPT` / `END ORIGINAL PROMPT` markers around the user-supplied text so the verbatim contract survives.
- **Add or change a classifier.** Edit `internal/flights/flight-monitor.yaml`: one Choice question per classifier, with its choices, `notify_on`, and `min_confidence`. The `planner`, `executor`, `reviewer`, and `commit` roles are required (`parseMonitorConfig`, `internal/flights/monitor_config.go`), and a test keeps the shipped file valid. The engine supports Choice questions and `notify_on` filtering only, so another question of that shape needs no Go change.
- **Supervise another role.** Add the role to `SessionRole` (`internal/flights/model.go`), give it classifiers in `flight-monitor.yaml`, list it in `monitoredSessions`, `notifiesEveryTurn`, `pilotJobForRole`, and the per-role check dispatch in `processMonitorWork` (`internal/flights/monitor.go`), add it to `pilotRecipientRoles` and the roles `deliverFlightMessageLocked` accepts (`internal/flights/pilot.go`) and to the role switch in `buildJevRequest` (`internal/flights/monitor_jev.go`), and add its label to `ROLE_LABEL` (`assets/dashboard/src/lib/flights.ts`).
- **Add a resource step to dispose.** Extend `disposal.Service.Request` for any workspace-wide step that the dashboard dispose-all path should also gain (force-purge and chat-delete already are), or pass `Observe func(ResourceOutcome)` per call if the step is flight-only. Keep remote-branch ops behind the caller's `ctx`; everything else runs on an independent context so HTTP client disconnects don't abort cleanup.
- **Expose a new flight field on the dashboard.** Add it to `contracts.FlightDetailResponse` and `contracts.FlightSummaryResponse` in `internal/api/contracts/flights.go`, run `go run ./cmd/gen-types`, render it in `FlightDetailPage.tsx` or the relevant list column. Never edit `types.generated.ts` by hand.
- **Change how names are written.** Prompt wording and the name rules (fewer than 10 words, ≤80 runes, no control characters) live in `internal/flightname/flightname.go` (`Prompt`, `validateName`). The rename threshold, tick, and backoff cap are `renameThreshold`, `namingTick`, and `maxNamingBackoff` in `internal/flights/naming.go`; tests drive `runNamingPass` directly with a `fakeNamer` and a settable clock.
- **Move a workspace to a different flight.** Don't. A flight's `WorkspaceAssignment` is recorded at takeoff; replacing it would let dispose clean the wrong workspace. Add a new flight instead.
