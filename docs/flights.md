# Flights

## What it does

A flight is the durable record of a manually advanced unit of work: a backlog item becomes one workspace, one planner session, one executor session, and one commit session, in that order, only when the user moves the workflow forward. A persistent pilot session supervises the planner; the monitor classifies completed planner responses through Jev and notifies the pilot of interesting or uncertain turns. Two shared subsystems back it — a destructive-cleanup service and a local-target spawn launcher — so destructive disposal and the local spawn path are not private to flights.

## Pilot and monitor

Takeoff is available only from backlog. Once workspace assignment moves the flight
to planning, takeoff cannot be repeated, even after a spawn failure or loss of a
session or workspace. Partial outcomes remain visible. Pilot spawn success is
persisted before attempting the planner. The pilot model is flight-manager
configuration, not part of a flight: `flight_pilot.target`, set in Settings >
Flights > Pilot Supervision and read at each takeoff. Flights never carry a
pilot model and there is no fallback to the planner model. When it is unset or
not chat-capable, takeoff returns 409 before allocating a workspace or spawning
a session. Pilot chatter does not replace planner/executor activity in the
flight list.

Classification waits for the harness to complete a planner turn, then sends all
top-level assistant response text from that turn, in order. Tool output, thinking,
and child-agent responses are excluded. Codex completion summaries can omit earlier
response blocks, so the monitor retains those blocks from the turn's records.
Pending pilot guidance rechecks planner availability and both sessions' workspace
membership at delivery, including after an explicit retry.

Restarting the pilot or planner from the dashboard (`POST /api/sessions/{id}/restart`)
disposes the old session and spawns a replacement seeded from the same conversation
record. The flight follows: the assignment moves to the new session ID, the replaced
ID joins `prior_session_ids`, and retained turns and messages are re-pointed so the
subscription resumes after the retained cursor, pending deliveries reach the
replacement, and pilot decisions still validate. The seeded turns are not
classified again. Ingestion errors (`monitor: session <id>: …`) are recorded once
per distinct error, not on every recovery tick, and clear when that session's
subscription succeeds or the session is replaced.

Planner ingestion and classification run separately. Pending turns survive restart
and explicit retry appends a new attempt using the current YAML. Notifications
retain source session/record ranges, the response, saved question/choice definitions,
confidence, the turn's spec/plan report and its check, and durable conversation path. The history exposes those
definitions even after YAML edits. Delivery is persisted before sending; a send
interrupted by daemon shutdown becomes `unknown` and cannot be blindly retried.
Queued outcomes are reconciled against the recipient runtime during monitor
reconciliation (including the 30-second recovery tick). Accepted notifications are
deduplicated by source turn and are not resent on recovery. Invalid retained IDs,
source references, or statuses make snapshot loading fail without rewriting it.

The direct Jev request uses keyed question and criterion objects, preserving YAML
choice order. The TypeSafe API key comes only from configured provider secrets
and is never saved with evidence. Live classifier accuracy and the live pilot round trip require manual
acceptance; fake-server tests establish transport and recovery behavior only.

The flight starts one persistent **pilot** chat session in the planner's workspace. The daemon delivers interesting or uncertain classifications to that chat, including a notification ID. The pilot's final response is one JSON decision, such as `{"notification_id":"msg-…","guidance":"Check the spec."}`. A null guidance value leaves the planner alone; the initial acknowledgement is `{"guidance":null}`. Ordinary prose, malformed JSON, unknown fields, and blank guidance produce visible decision errors and never trigger delivery.

The flight worker subscribes to both assigned chats. Only planner responses go to Jev. Completed pilot responses are retained and interpreted inside the daemon; there is no CLI command or HTTP return endpoint. The worker checks current pilot/planner assignment, workspace membership, planner availability, and a delivered notification belonging to the current planner. It persists guidance before calling the planner chat runtime directly. The planner sees `[Pilot]` attribution; retained evidence keeps the exact unprefixed text, source pilot turn, notification ID, and delivery outcome. Pilot turns use `skipped` because they are not classified by Jev. Replaying a pilot response deduplicates its message by source session and turn boundary. Unknown crash-time delivery is never blindly resent. Native questions and permissions remain manual.

The monitor subscribes to the planner's chat runtime (via `Runtime.Subscribe`), extracts the full response of each completed turn (Claude `result` or Codex `turn/completed`), and sends it directly to the Jev HTTP API. The schema and routing rules live in `~/.schmux/flight-monitor.yaml`; the file is read and validated before every classification, and an invalid file produces a visible monitor error without silently using old questions. The initial file ships two Choice questions: `attention` (needs attention vs routine) and `planning_artifacts` (which planning documents the response claims are written). A turn wakes the pilot when any answer's confidence falls below its `min_confidence` threshold or any answer's choice is in the classifier's `notify_on` list. Failed or interrupted turns notify the pilot with the harness outcome without asking Jev to infer it. Successful empty turns record `skipped` and never call Jev.

Configure flight naming and the TypeSafe API key under **Settings → Flights**.
The Flights page's **Settings** link opens this tab. The key is in **Pilot Supervision**.
Set, update, and removal use the standard password prompt and config-update API;
only the presence of a stored key is returned to the browser. The key is saved in
`secrets.json` under `providers.typesafe.TYPESAFE_API_KEY`, using the same owner-only,
atomic secret-file storage as other providers. It is read for each classification,
so changes apply without restarting the daemon. Removing the stored key leaves
classification unconfigured. Existing failed turns can be retried from monitor history.
A missing key is a visible classification failure, not a routine ruling. Neither
Claude nor the TypeSafe Claude skill sits in the production classification path.

The Flights page displays a warning above the list and forms when the daemon
cannot resolve the key or cannot read or validate `flight-monitor.yaml`. The warning
links to the Flights settings tab. This check comes from GET `/api/config`
and uses the same configured provider secret as classification.
The local readiness check does not call Jev or verify the key with the provider.

## Architecture decisions

- **Sole-writer rule.** `flights.Manager` is the only writer of `~/.schmux/flights.json`. Handlers, transition functions, and the persistence layer never edit flight state directly — they call into the manager and serialize the resulting snapshot atomically (`internal/flights/manager.go:108`). A pending `Operation` is persisted before any external call, then re-persisted with its outcome, so a daemon crash leaves a visible attempt.
- **Manual workflow.** No session signal, chat activity, transcript assessment, or elapsed time advances a flight. The user explicitly clicks each arrow. `execution` requires a verified spec/plan report and rechecks both files against the placement contract; it never inspects planning quality or skill compliance.
- **The skills choose where the spec and plan go.** Schmux never dictates a location. It tells the planner to let `superpowers:brainstorming` and `superpowers:writing-plans` place the documents and to report the absolute paths, then deterministically checks each report and surfaces any violation in the monitor history and the pilot's notification.
- **Two independent state axes.** `WorkflowState` is the stage axis (`backlog`/`planning`/`executing`/`completing`/`done`). `CleanupState` is the destructive-cleanup axis (`idle`/`disposing`). A `done` workflow with `disposing` cleanup is valid and retryable. `requireIdle` rejects transitions while cleanup is in flight (`internal/flights/transitions.go:87`).
- **Workspace allocation belongs to takeoff.** A backlog takeoff calls `workspace.Manager.GetOrCreateWithLabel`. Planning does not offer takeoff again; a failed spawn or missing resource stays visible without respawning sessions or reallocating a workspace.
- **Per-flight op-lock, no global lock during external calls.** `flights.Manager.mu` is held only across in-memory edits and persistence. The slow `SpawnLocal` and `DisposeAll` calls run under a per-flight mutex from `opLocks`, so two transitions on the same flight never interleave while two transitions on different flights never contend.
- **One cleanup path.** `disposal.Service.DisposeAll` is the only place that sequences workspace disposal. Dashboard `dispose-all` and flight `dispose` both call it; neither holds its own copy. Force-purge semantics come from exposing `workspace.Manager.DisposeForcePurge` rather than reimplementing filesystem deletion. Remote refs are never modified.
- **One local spawn path.** `spawnlaunch.Launcher` validates the target, checks chat-capability, resolves fence, resolves persona/style context, calls `session.Manager.Spawn`, writes a spawn log, and broadcasts on success. The dashboard's multi-target `/api/spawn` handler and `flights.Manager.Takeoff`/`EnterExecution`/`EnterCompletion` both use it.
- **Delimited original prompt.** The planner/executor prompts reproduce the original flight prompt byte-for-byte between `----- BEGIN/END ORIGINAL PROMPT -----` markers (`internal/flights/prompts.go:6`) so the flight operator can review the exact wording without diffing composited instructions.
- **No new event channel.** The existing `/ws/dashboard` payload gains a full `flights` array on its initial and debounced snapshots. Clients replace the array from every payload; they never poll. The detail route refetches after a reconnect broadcast that mentions its flight. The list's activity line reads `sessionsById` from the same `SessionsContext`; no polling, no second channel.
- **Dispose confirmation matches workspace ID.** `POST /api/flights/{flightID}/dispose` requires the body's `workspace_id` to match the flight's recorded workspace; a mismatch returns 409 and performs no cleanup. The dashboard consequence modal names the workspace and everything destruction will take (`FlightDisposeModal.tsx`). A flight with no workspace removes at once with a plain Remove confirm.
- **Dispose is the only removal.** Dispose is the sole removal action; there is no separate cancellation state or record-only deletion: the flight record always leaves the list when its resources do, or, when there are no resources, immediately. No path may orphan a workspace from its flight or vice versa; the dashboard's `DELETE /api/flights/{id}` route is unregistered for the same reason.
- **Daemon-generated names.** A flight's `short_name` is written only by the background namer (`internal/flights/naming.go`) through the `flight-name` oneshot (`internal/flightname`); create and update requests no longer carry it. Users never type a name, and creating or editing a flight never waits on the LLM. A flight with empty `name_prompt` is a placeholder — every flight that predates the namer, or was created while naming was off — and is named on the next pass once `flight_name.target` is set, so no migration code exists.
- **Rename on 5% drift from `name_prompt`, not from the last edit.** `promptChange(name_prompt, prompt) >= renameThreshold` (rune Levenshtein divided by the longer string). Comparing against the prompt the current name came from makes many small edits that add up to a real change still trigger a rename, while a typo fix never does.
- **Stale results are dropped, not merged.** The pass snapshots the prompt, calls the LLM outside every manager lock and the per-flight op-lock (so a takeoff never waits on naming), then writes only if the prompt still matches the snapshot. A changed prompt or a disposed flight discards the result; the next pass picks it up.
- **Naming failures live in `name_error`, not `Operations`.** Operations are workflow transitions and `LastError` is derived from them; mixing naming failures in would muddy both. Retries back off 1m → 1h per flight in memory only (`nextBackoff`); a success, a prompt change, or a daemon restart starts the backoff over. An identical repeated error does not rewrite `flights.json` or broadcast.
- **No model means naming is off, not an error.** An empty `flight_name.target` yields `ErrNamingOff`: no `name_error`, no backoff, the ID label stays. There is deliberately no fallback to `branch_suggest` targets. A configured target that doesn't resolve (`ErrTargetNotFound`) is a real failure and shows as `name_error`. A name the model returns that breaks a rule (empty, control characters, 10 or more words, over 80 characters) is `ErrInvalidName`; its `name_error` states the broken rule and quotes the rejected name. Names are not required to be unique.

## Gotchas

- **A flight's resources include any session in the workspace.** `dispose` enumerates sessions live in the workspace at call time, not only the planner/executor/commit assignments. Other sessions stored under the same workspace ID that belong to a different flight are left in place.
- **Chat history is deleted only by dispose.** Ordinary `dispose-all` keeps the conversation record (default retention). Dispose passes `ChatSessionIDs` (recorded current + prior IDs) plus live-workspace sessions into `disposal.Service`, which calls `chat.DeleteConversations` only when that list is non-empty.
- **Force-purge rejects on stuck sessions.** `disposal.Service` calls `Workspaces.DisposeForcePurge` only after every session dispose succeeds; otherwise it reverts the workspace status and returns the session errors joined. A live session is never left behind a purged workspace.
- **Workspace dispose-guard rails are bypassed by force-purge.** Uncommitted changes, unpushed commits, and recycling all lose to `DisposeForcePurge`. The flight branch is removed at the end via `Workspaces.CleanupFlightBranch` only when no other worktree still references it; remote refs are never touched.
- **Restart preserves the `disposing` state.** Daemon restart leaves cleanup-state and recorded outcomes intact; an incomplete dispose can be retried explicitly. Already-absent resources count as cleaned.
- **The flight edit form lets the user pick a non-listed value.** Every recorded field (including planner/executor models) is editable in every stage; a value that has since been removed from config stays selectable on the flight that recorded it (`FlightEditForm.tsx`).
- **Stage is editable directly.** Saving a new `workflow_state` does not run a transition; it only writes the field. To advance, click the action button.
- **Workspace header flight button is conditional.** It appears only when the current workspace appears in the derived `flightByWorkspaceId` map (recorded assignments, not lifecycle hints). Unassigned workspaces render no flight control — there is no "create flight for this workspace" button on the header.
- **`order` is meaningful only in backlog.** Section membership and manual ordering use `workflow_state`, including backlog flights that retain a workspace after editing. `POST /api/flights/order` requires every backlog ID and rejects flights in another workflow state. Started flights use session activity order.
- **Activity line uses the sidebar's adjusted timestamp rule.** The list ranks started flights by `last_output_at` minus one hour when the session is in progress, exactly as `lib/workspaceSort.ts:24` does for the sidebar workspace time sort. The shared `sessionActivityTime`/`latestActivityTime` helpers in `workspaceSort.ts` are the single source. `flightActivity` also records the in-progress result, and the line reads "Working" from it, so the wording and the order agree. A resolved session with no output yet still gets a linked line; "session gone" means no role session resolved at all.
- **One status line per started row.** The line combines the recorded stage, selected role, observed session state, and relative output time. Cleanup replaces it with "Disposing"; no assignments renders `<Stage> · No session`. There are no list status pills or resource stacks. The flight name opens the resource inventory on the detail page. Section headers explain manual backlog order and the adjusted activity order.
- **Sapling workspace labels are fixed at takeoff.** Takeoff sets the workspace label from the flight's `short_name` at that moment (`internal/flights/transitions.go:230-233`, `displayName`). Git repos get branch `schmux/flight/<ID>` and no label. A later rename does not relabel a Sapling workspace; the dashboard surfaces the current name via `flightLabel` everywhere else.
- **`StartNaming` must run after `wireCallbacks`.** The oneshot path resolves targets through the model manager that `wireCallbacks` installs (`oneshot.SetModelManager`, `models.SetDefault`). Starting the namer earlier makes the first pass report every placeholder as "model not found"; `Run` starts it right after `wireCallbacks` (`internal/daemon/daemon.go:479`).
- **`short_name` in a request is silently ignored.** The flight handlers don't use `DisallowUnknownFields`, so an old client sending `short_name` gets a 200 and no change.
- **`name_error` shows only on the list rows and the detail page.** The workspace header button and toasts show `flightLabel` alone.

## Common modification patterns

- **Add a new transition.** Add an `OperationAction` constant in `internal/flights/model.go`, a `(m *Manager) <Name>(ctx, id)` on `manager.go`, a HTTP handler in `internal/dashboard/handlers_flights.go`, a route in `registerMutatingRoutes`, a typed client function in `assets/dashboard/src/lib/flights.ts` (the file that already houses `flights-api.ts`'s re-export), a button in `FlightActions.tsx`, and an `Action`→`label` mapping in `assets/dashboard/src/lib/flights.ts`. Persist a pending `Operation` before any external call, then its outcome.
- **Change a role's prompt.** Edit `internal/flights/prompts.go` — keep the `BEGIN ORIGINAL PROMPT` / `END ORIGINAL PROMPT` markers around the user-supplied text so the verbatim contract survives.
- **Add a resource step to dispose.** Extend `disposal.Service.Request` for any workspace-wide step that the dashboard dispose-all path should also gain (force-purge and chat-delete already are), or pass `Observe func(ResourceOutcome)` per call if the step is flight-only. Keep remote-branch ops behind the caller's `ctx`; everything else runs on an independent context so HTTP client disconnects don't abort cleanup.
- **Expose a new flight field on the dashboard.** Add it to `contracts.FlightDetailResponse` and `contracts.FlightSummaryResponse` in `internal/api/contracts/flights.go`, run `go run ./cmd/gen-types`, render it in `FlightDetailPage.tsx` or the relevant list column. Never edit `types.generated.ts` by hand.
- **Change how names are written.** Prompt wording and the name rules (fewer than 10 words, ≤80 runes, no control characters) live in `internal/flightname/flightname.go` (`Prompt`, `validateName`). The rename threshold, tick, and backoff cap are `renameThreshold`, `namingTick`, and `maxNamingBackoff` in `internal/flights/naming.go`; tests drive `runNamingPass` directly with a `fakeNamer` and a settable clock.
- **Move a workspace to a different flight.** Don't. A flight's `WorkspaceAssignment` is recorded at takeoff; replacing it would let dispose clean the wrong workspace. Add a new flight instead.
