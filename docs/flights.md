# Flights

## What it does

A flight is the durable record of a manually advanced unit of work: a backlog item becomes one workspace, one planner session, one executor session, and one commit session, in that order, only when the user moves the workflow forward. Two shared subsystems back it — a destructive-cleanup service and a local-target spawn launcher — so destructive disposal and the local spawn path are not private to flights.

## Architecture decisions

- **Sole-writer rule.** `flights.Manager` is the only writer of `~/.schmux/flights.json`. Handlers, transition functions, and the persistence layer never edit flight state directly — they call into the manager and serialize the resulting snapshot atomically (`internal/flights/manager.go:108`). A pending `Operation` is persisted before any external call, then re-persisted with its outcome, so a daemon crash leaves a visible attempt.
- **Manual workflow.** No session signal, chat activity, transcript assessment, or elapsed time advances a flight. The user explicitly clicks each arrow. `execution` only verifies that the named artifact exists, is readable, and is non-empty; it never inspects planning quality or skill compliance.
- **Two independent state axes.** `WorkflowState` is the stage axis (`backlog`/`planning`/`executing`/`completing`/`done`/`cancelled`). `CleanupState` is the destructive-cleanup axis (`idle`/`terminating`). A `cancelled` or `done` workflow with `terminating` cleanup is valid and retryable. `requireIdle` rejects transitions while cleanup is in flight (`internal/flights/transitions.go:87`).
- **Workspace reuse via the manager.** Takeoff calls `workspace.Manager.GetOrCreateWithLabel` every time. The manager reuses an existing workspace whose branch matches and has no active sessions; allocates a fresh one otherwise. Retries after a successful planner — or after a user disposed the recorded workspace by hand — therefore converge without flight-side book-keeping.
- **Per-flight op-lock, no global lock during external calls.** `flights.Manager.mu` is held only across in-memory edits and persistence. The slow `SpawnLocal` and `DisposeAll` calls run under a per-flight mutex from `opLocks`, so two transitions on the same flight never interleave while two transitions on different flights never contend.
- **One cleanup path.** `disposal.Service.DisposeAll` is the only place that sequences workspace disposal. Dashboard `dispose-all` and flight `terminate` both call it; neither holds its own copy. Force-purge semantics come from exposing `workspace.Manager.DisposeForcePurge` rather than reimplementing filesystem deletion. Remote refs are never modified.
- **One local spawn path.** `spawnlaunch.Launcher` validates the target, checks chat-capability, resolves fence, resolves persona/style context, calls `session.Manager.Spawn`, writes a spawn log, and broadcasts on success. The dashboard's multi-target `/api/spawn` handler and `flights.Manager.Takeoff`/`EnterExecution`/`EnterCompletion` both use it.
- **Delimited original prompt.** The planner/executor prompts reproduce the original flight prompt byte-for-byte between `----- BEGIN/END ORIGINAL PROMPT -----` markers (`internal/flights/prompts.go:6`) so the flight operator can review the exact wording without diffing composited instructions.
- **No new event channel.** The existing `/ws/dashboard` payload gains a full `flights` array on its initial and debounced snapshots. Clients replace the array from every payload; they never poll. The detail route refetches after a reconnect broadcast that mentions its flight.
- **Termination confirmation matches workspace ID.** `POST /api/flights/{flightID}/terminate` requires the body's `workspace_id` to match the flight's recorded workspace; a mismatch returns 409 and performs no cleanup. The dashboard modal names the workspace and every consequence (`FlightTerminateModal.tsx`).
- **Delete vs terminate.** Delete removes the flight record in any state; resources stay in place. Terminate cleans every assigned live resource and only removes the flight record after every resource step succeeds. The two are independent.

## Gotchas

- **A flight's resources include any session in the workspace.** `terminate` enumerates sessions live in the workspace at call time, not only the planner/executor/commit assignments. Other sessions stored under the same workspace ID that belong to a different flight are left in place.
- **Chat history is deleted only by terminate.** Ordinary `dispose-all` keeps the conversation record (default retention). Termination passes `ChatSessionIDs` (recorded current + prior IDs) plus live-workspace sessions into `disposal.Service`, which calls `chat.DeleteConversations` only when that list is non-empty.
- **Force-purge rejects on stuck sessions.** `disposal.Service` calls `Workspaces.DisposeForcePurge` only after every session dispose succeeds; otherwise it reverts the workspace status and returns the session errors joined. A live session is never left behind a purged workspace.
- **Workspace dispose-guard rails are bypassed by force-purge.** Uncommitted changes, unpushed commits, and recycling all lose to `DisposeForcePurge`. The flight branch is removed at the end via `Workspaces.CleanupFlightBranch` only when no other worktree still references it; remote refs are never touched.
- **Restart preserves the `terminating` state.** Daemon restart leaves cleanup-state and recorded outcomes intact; an incomplete terminate can be retried explicitly. Already-absent resources count as cleaned.
- **The flight edit form lets the user pick a non-listed value.** Every recorded field (including planner/executor models) is editable in every stage; a value that has since been removed from config stays selectable on the flight that recorded it (`FlightEditForm.tsx`).
- **Stage is editable directly.** Saving a new `workflow_state` does not run a transition; it only writes the field. To advance, click the action button.
- **Workspace header flight button is conditional.** It appears only when the current workspace appears in the derived `flightByWorkspaceId` map (recorded assignments, not lifecycle hints). Unassigned workspaces render no flight control — there is no "create flight for this workspace" button on the header.
- **`order` is meaningful only in backlog.** Once a flight has a `WorkspaceAssignment`, ordering ignores it. `POST /api/flights/order` rejects IDs from flights that already have a workspace.

## Common modification patterns

- **Add a new transition.** Add an `OperationAction` constant in `internal/flights/model.go`, a `(m *Manager) <Name>(ctx, id)` on `manager.go`, a HTTP handler in `internal/dashboard/handlers_flights.go`, a route in `registerMutatingRoutes`, a typed client function in `assets/dashboard/src/lib/flights-api.ts`, a button in `FlightActions.tsx`, and an `Action`→`label` mapping in `assets/dashboard/src/lib/flights.ts`. Persist a pending `Operation` before any external call, then its outcome.
- **Change a role's prompt.** Edit `internal/flights/prompts.go` — keep the `BEGIN ORIGINAL PROMPT` / `END ORIGINAL PROMPT` markers around the user-supplied text so the verbatim contract survives.
- **Add a resource step to terminate.** Extend `disposal.Service.Request` for any workspace-wide step that the dashboard dispose-all path should also gain (force-purge and chat-delete already are), or pass `Observe func(ResourceOutcome)` per call if the step is flight-only. Keep remote-branch ops behind the caller's `ctx`; everything else runs on an independent context so HTTP client disconnects don't abort cleanup.
- **Expose a new flight field on the dashboard.** Add it to `contracts.FlightDetailResponse` and `contracts.FlightSummaryResponse` in `internal/api/contracts/flights.go`, run `go run ./cmd/gen-types`, render it in `FlightDetailPage.tsx` or the relevant list column. Never edit `types.generated.ts` by hand.
- **Move a workspace to a different flight.** Don't. A flight's `WorkspaceAssignment` is recorded at takeoff; replacing it would let termination clean the wrong workspace. Add a new flight instead.
