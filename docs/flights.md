# Flights

## What it does

A flight is the durable record of a unit of work: a backlog item becomes one workspace, a planner session, an executor session, one or more reviewer sessions, and a commit session, in that order (`backlog → planning → executing → reviewing → completing`). The pilot advances the flight from planning to executing and from executing to reviewing on its own judgement, from evidence; the user starts the commit. The manual phase actions stay available as overrides. Completing is the last phase: the commit is ready, and the flight stays there, owning its workspace and sessions, until the user rebases, pushes, merges, and disposes it. A persistent pilot session supervises the working session of each phase; the monitor classifies completed working-session responses through Jev and notifies the pilot of interesting or uncertain planner turns and of every executor, reviewer, and committer turn. Two shared subsystems back it — a destructive-cleanup service and a local-target spawn launcher — so destructive disposal and the local spawn path are not private to flights.

## Pilot and monitor

Takeoff is available only from backlog. Once workspace assignment moves the flight
to planning, takeoff cannot be repeated, even after a spawn failure or loss of a
session or workspace. Partial outcomes remain visible. Pilot spawn success is
persisted before attempting the planner. The pilot model is flight-manager
configuration, not part of a flight: `flight_pilot.target`, set in Settings >
Flights > Pilot Supervision and read at each takeoff. Flights never carry a
pilot model and there is no fallback to the planner model. When it is unset or
not chat-capable, takeoff returns 409 before allocating a workspace or spawning
a session. Pilot chatter does not replace planner/executor activity in the
flight list.

Classification waits for the harness to complete a planner turn, then sends all
top-level assistant response text from that turn, in order. Tool output, thinking,
and child-agent responses are excluded. Codex completion summaries can omit earlier
response blocks, so the monitor retains those blocks from the turn's records.
Pending pilot guidance rechecks planner availability and both sessions' workspace
membership at delivery, including after an explicit retry.

Restarting the pilot or planner from the dashboard (`POST /api/sessions/{id}/restart`)
disposes the old session and spawns a replacement seeded from the same conversation
record. The flight follows: the assignment moves to the new session ID, the replaced
ID joins `prior_session_ids`, and retained turns and messages are re-pointed so the
subscription resumes after the retained cursor, pending deliveries reach the
replacement, and pilot decisions still validate. The seeded turns are not
classified again. Ingestion errors (`monitor: session <id>: …`) are recorded once
per distinct error, not on every recovery tick, and clear when that session's
subscription succeeds or the session is replaced.

Planner ingestion and classification run separately. Pending turns survive restart
and explicit retry appends a new attempt using the classifier definitions of the
running build. Notifications
retain source session/record ranges, the response, saved question/choice definitions,
confidence, the turn's spec/plan report and its check, and durable conversation path. The history exposes those
definitions even after a later schmux build changes them. Delivery is persisted before sending; a send
interrupted by daemon shutdown becomes `unknown` and cannot be blindly retried.
Queued outcomes are reconciled against the recipient runtime during monitor
reconciliation (including the 30-second recovery tick). Accepted notifications are
deduplicated by source turn and are not resent on recovery. Invalid retained IDs,
source references, or statuses make that flight's row invalid: the loader keeps
the raw row aside and out of the flight list rather than failing the load (see
"Gotchas").

The direct Jev request uses keyed question and criterion objects, preserving YAML
choice order. The TypeSafe API key comes only from configured provider secrets
and is never saved with evidence. Live classifier accuracy and the live pilot round trip require manual
acceptance; fake-server tests establish transport and recovery behavior only.

The flight starts one persistent **pilot** chat session in the planner's workspace. The daemon delivers interesting or uncertain classifications to that chat. The pilot's final response is one JSON decision carrying exactly one of three forms: guidance (`{"to":"planner","guidance":"Check the spec."}`), a request for the next reviewer (`{"next_reviewer":"…"}`, see "Supervising review"), or a stop (`{"stop":"…"}`, see "Pilot stop"). The pilot does not copy a notification ID; a `notification_id` field from a pilot prompted by an earlier build is accepted and ignored. Every message schmux sends the pilot (a notification or a launch notice) restates the decision contract (`decisionContract`, `internal/flights/prompts.go`), so a pilot whose takeoff prompt came from an earlier build follows the current rules without being restarted. `to` names the recipient's role and is required whenever guidance is a string; `next_reviewer` and `stop` take no `to`. `to` may name any working role whose session the flight has started (`planner`, `executor`, `reviewer`, `commit`): every started session stays addressable in every later phase, so the pilot can send the planner back to its plan during execution or ask the executor a question during review. The daemon resolves the role to the currently assigned session, and a response cannot name a session ID. A null guidance value leaves everyone alone, and any `to` with it is ignored. More than one form, malformed JSON, unknown fields, blank text, and a missing, unknown, or not-yet-started `to` produce visible decision errors (the error names the roles the flight has started) and never trigger delivery or a spawn. There is no default recipient. The pilot is the flight's orchestrator: every completed pilot response is read for a decision, whatever prompted it (a notification, the execution or review notice, or the user), and schmux does not track which message a turn answered. A response that is not a JSON object (a code fence around one is stripped) is the pilot talking to the user; it is retained as `skipped`, not parsed, and sends nothing, and it is not an error. A decision that cannot be applied (malformed, an invalid sender or recipient, or any other validation failure) is recorded on the pilot's turn as a visible error and sends nothing to anyone; schmux does not send the pilot a rejection to answer again (that loop was removed on 2026-10-28, see "Architecture decisions"). A valid message that definitely fails to send is different: the original sender is told, as described next.

**Undelivered messages.** When an agent-to-agent message (guidance from the pilot, or any message with a sender and a recipient assigned to the flight) definitely fails to send, schmux sends the original sender the plain-text notification `Your message to <recipient> was not delivered: <send error>.` The recipient is the session ID on the original message and the error is the one the send returned. This holds whichever agent sent the message, and applies both to a failure before the message is queued (the recipient is not running, or the sender and recipient are outside the flight workspace) and to a send that fails once attempted. Validation errors and ambiguous delivery outcomes (a send interrupted by daemon shutdown, status `unknown`) produce no notification, and a message without a sender, such as a notification or a failure notice itself, never produces one. Successful delivery, retries, and the dashboard are unchanged. The user sees the error on the flight's story and can retry the turn there once the cause is fixed; the pilot decides again whenever it has something to say.

The flight worker subscribes to the pilot's chat and to every started working session's chat (`monitoredSessions`): the planner, the executor, the current reviewer, and the committer, each from the phase that starts it until the flight leaves `completing`. The pilot orchestrates all of them, so the monitor follows all of them; which turns wake the pilot is decided per turn (see below). The reviewer that was current when the user entered completion is recorded on the completion operation as a `reviewer` resource, as history. Only working-session responses go to Jev. Completed pilot responses are retained and interpreted inside the daemon; there is no CLI command or HTTP return endpoint. The worker checks current pilot and recipient assignment, workspace membership, and recipient availability. It persists guidance before calling the recipient's chat runtime directly. Guidance still pending when the phase changes keeps its recipient while that session still holds its role. The recipient sees `[Pilot]` attribution; retained evidence keeps the exact unprefixed text, source pilot turn, and delivery outcome. Pilot turns use `skipped` because they are not classified by Jev. Replaying a pilot response deduplicates its message by source session and turn boundary. Unknown crash-time delivery is never blindly resent. Native questions and permissions remain manual.

The monitor subscribes to the planner's chat runtime (via `Runtime.Subscribe`), extracts the full response of each completed turn (Claude `result` or Codex `turn/completed`), and sends it directly to the Jev HTTP API. The schema and routing rules are part of the workflow and live in schmux itself, in `internal/flights/flight-monitor.yaml`, embedded in the binary. Every installation asks the same questions; nothing is installed into or read from `~/.schmux`, and users do not edit them. The definitions must include the `planner`, `executor`, `reviewer`, and `commit` roles; validation names a missing role (`flight-monitor: role "reviewer" is required`), and a test keeps the shipped file valid. The definitions are, for the planner, `attention` (needs attention vs routine) and `planning_artifacts` (which planning documents the response claims are written); for the executor, `attention` and `execution_state` (finished, stopped, or still working); for the reviewer, `review_state` (finished, fixing, blocked), `tests` (run and passed, run and failed, not run), `test_rules_review` (compliant, violations, not run), `changed_work` (changed, unchanged), and `artifacts_named` (named, incomplete); for the committer, `attention` and `completion_state` (committed, gate failed, working, blocked). A turn of the phase's own worker (the executor while executing, the reviewer while reviewing, the committer and the reviewer while completing) notifies the pilot on every turn, whatever the classifiers say; `execution_state` and every reviewer and committer classifier therefore have empty `notify_on` and exist to inform the pilot and the user. Every other followed turn (every planner turn, and an earlier phase's session the user is still talking to) wakes the pilot only when any answer's confidence falls below its `min_confidence` threshold or any answer's choice is in the classifier's `notify_on` list. Failed or interrupted turns notify the pilot with the harness outcome without asking Jev to infer it. A successful turn with no response text records `skipped`, never calls Jev, and does not notify, unless the daemon's own checks found a placement violation or the verified execution report in it.

### Automatic advancement

The pilot advances the flight itself: `planning → executing` and `executing → reviewing`. It does so with an explicit decision in its own completed turn — `{"advance":"executing"}` or `{"advance":"reviewing"}` — which the daemon reads like every other pilot decision. There is no other automatic transition. Takeoff stays the user's action, and completion stays the user's action: the pilot cannot ask for the backlog, for the commit, or for disposal, and it never starts the committer.

The decision carries no claim of readiness of its own; the pilot judges readiness from the evidence in front of it — the verified report, the workspace, the conversation — and a classifier's answer alone never advances a flight. The daemon checks that the decision is well formed, that it comes from the flight's current pilot and workspace, that the flight is in the phase the decision starts from, that cleanup is idle, that no transition is already pending, and that no pilot stop was recorded in the current phase visit. A rejected decision is a visible error on the pilot's turn; nothing is sent back to the pilot.

**Phase visits.** A flight records the visit it is in: the number of times it has changed state, and when the current visit began. Saving the same state changes nothing; editing away and back begins a new visit. A pilot turn is bound to a visit by its own start boundary — a Claude dispatch marker or a Codex `turn/started` record, taken from the record's own timestamp — not by whichever phase happens to be current when the turn is retained. A turn that began in an earlier visit cannot advance the current one, and a turn whose start is unknown or ambiguous cannot advance anything; both are visible errors. The same binding applies to the pilot's stop, so a stop from an earlier visit stays in the history without stopping a later one.

A stop decision without evidence of the current visit is rejected before changing the active stop. If the clock at phase entry does not advance beyond the last known boundary or persisted update, the visit is recorded with `phase_time_uncertain` and cannot bind turns for automatic decisions. The known boundary is retained across edits and reloads; clock recovery alone does not clear the uncertainty. A later phase entry with a strictly newer timestamp does. Manual phase actions remain available.

**Operation provenance.** An advance records an operation with the deciding pilot turn and its visit before the session is spawned, so deduplication rests on a durable record rather than on a message appended after the fact. The operation appears in the flight's story with its source turn, and a replayed decision, a recovered daemon, or a manual return to an earlier phase starts nothing: the decision is already consumed.

**Pending operations.** A transition that has not settled — its session may or may not exist — blocks every other way into the flight. The manual phase actions, the pilot's advance decision, and a direct stage edit all refuse while it is pending, and the refusal names the operation so the user can reconcile it. A spawn that failed definitely leaves the source phase and a failed operation, which the user may retry explicitly. A spawn whose outcome cannot be established leaves the operation pending instead, and a failed launch notice after a successful advance is reported without repeating the transition.

### Supervising execution

**Enter execution** records `execution_started_at`, fixes the report target (the verified plan path with its extension replaced by `-execution.md`, or `review/<flight-id>-execution.md` when no plan was verified; a later planner report never moves it), spawns the executor with a prompt that tells it to run `superpowers:executing-plans`, use no subagents, create no worktrees, make no commits, skip `superpowers:finishing-a-development-branch`, follow the how-to-work rules (`executionDiscipline` in `internal/flights/prompts.go`: run each test once, rerun one only with the pilot's permission (asked by ending the turn), and never loop it; report a failing test rather than hunting flakiness, checking whether it predated the change, or changing the test to pass; start a long suite once and never restart, kill, sleep on, or poll it; never revert or discard changes unless a human asks; stop and report when a test fails or work is blocked), and write the report when finished, and queues an `execution_notice` for the pilot. The notice tells the pilot an executor has launched, names its session and the report path, and says guidance can now go to `executor`; it needs no decision. What to do with each executor turn arrives in that turn's notification: compare the work with the spec and plan, send the executor guidance about substantial drift, check the conversation for actual use of the execution skill, and do not implement, commit, edit the spec or plan, dispose the flight, or wipe the workspace; the turn whose report verifies also tells the pilot that execution has finished and that it should compare the work with the spec and plan and, when it is complete and nothing is unresolved, request the review phase with an advance decision.

While the flight is `executing`, every completed executor turn notifies the pilot, whatever the classifiers say: most executions end in one turn, and the pilot's comparison with the plan is the drift check. The planner does not check executed work (a fresh reviewer does); it stays assigned, the monitor keeps following it, its turns remain classifier-gated, and the pilot may still address it, for example to have the plan revised when the executor finds it wrong. A failed classification (no key, invalid YAML, Jev error) does not hold the notification back: it goes out with `Classification failed: <error>` in place of answers, and a later retry records its answers in monitor history only. Executor notifications add a **Skill check** (`executing-plans invoked at record N` from a Claude `Skill` tool call, `executing-plans skill file read at record N` from a Codex command that reads the skill file, or `executing-plans not found`; only the executor's records count) and a **Report check** (`not written yet`, `verified: <path>`, or the failure reason). The report counts only if it is a regular, nonempty file inside the workspace modified after execution started, so a file left from before does not; git-ignore is not checked. The first turn whose check passes sets `report_path` on the flight; a verified report is how the daemon knows execution has finished. No Jev answer or executor claim substitutes for it. The flight stays `executing` until the pilot requests the review phase with an advance decision, or the user clicks **Enter review**; the manual action does not require a verified report. Supervision runs at turn boundaries only; it does not stop a commit or subagent as it happens, and questions and permissions stay human-answered.

The flight detail page shows the report target (marked not yet verified until `report_path` is set), the same activity line as the list, and each executor turn's skill and report checks. The activity line leads with a session waiting on a native question or permission over one with newer output.

### Supervising review

**Enter review** is offered on an `executing` flight, and the pilot's advance decision starts the same transition; the daemon requires only a workspace and idle cleanup, and there is no confirmation. It records `review_started_at`, moves the flight to `reviewing`, spawns a fresh **reviewer** chat session with the planner's model (`planner_model`), and queues a `review_notice` for the pilot naming the reviewer; it needs no decision. The reviewer has no history from the planner, the executor, or an earlier reviewer. Its prompt (`ReviewerPrompt`, `internal/flights/prompts.go`) tells it to review the work as the plan's author would and fix every problem in place without starting over; check reuse, the repository's patterns and style or review skills, docs, and tests that test behavior; verify every acceptance criterion in the spec with evidence; run the repository's own tests and checks and rerun them after its last change; run the `test-rules-review` skill until clean; put the artifacts the acceptance criteria name under `review/` and write a self-contained HTML account at `review/<plan file stem>-review.html` in the workspace; and end by saying whether it changed anything and listing the summary and artifacts, without committing, pushing, rebasing, finalizing, or changing the phase. It carries the executor's how-to-work rules and the `[Pilot]` note, and names the spec, plan, and verified report (or says no verified report exists). The planning steps now include writing an **Acceptance criteria** section in the spec before the coherence check, so the reviewer has criteria to verify; schmux never reads that section.

While the flight is `reviewing`, every completed reviewer turn notifies the pilot with the reviewer classifiers' answers and a **Skill check** (`test-rules-review invoked at record N`, `test-rules-review skill file read at record N`, or `test-rules-review not found`; only the reviewer's own records count). The notification carries the pilot's review job: hold the reviewer to its prompt, look in the reviewer's conversation for the test commands actually run after the last change and the skill actually invoked rather than trusting its claim, send guidance with `"to": "reviewer"`, ask for the next reviewer when this one changed something, and record a stop if the chain has gone off the rails.

When a reviewer reports it changed something, the pilot sends `next_reviewer`: a paragraph saying what the last reviewer changed and what to re-check. The daemon records a `next_review` operation, spawns a fresh reviewer whose prompt is the reviewer prompt plus that paragraph (it reviews the whole change again, not only the fix), moves the `reviewer` assignment to it with the previous session ID in `prior_session_ids`, records the paragraph as a `next_reviewer` message, and queues another `review_notice`. The superseded reviewer keeps running; nothing is sent to it or done to it. The review has converged when a reviewer reports it changed nothing and everything it checked passed; the pilot then sends no `next_reviewer`. Nothing caps the chain: a chain that does not converge is the pilot's to report with a stop.

The flight list and detail page show the latest reviewer classification in words ("Reviewer reports: finished, tests run and passed, test-rules-review compliant, changed nothing, artifacts named"), derived from the retained monitor turns as `review_status`. Superseded reviewers count: after a `next_reviewer`, the previous reviewer's reading stays until the new reviewer has a classified turn. Each classifier has its own words, so `not_run` reads "tests not run" or "test-rules-review not run". The detail page also shows the pilot's latest delivered or queued guidance ("Pilot to Reviewer: …", `pilot_guidance`) in its own line; the list does not, and the story keeps every message. The detail page lists the current and prior reviewer sessions among the resources. Schmux does not run the tests, read the spec, plan, report, or test files, check whether the summary or any artifact exists, link the summary, or block a transition on any classification; the reviewer's chat already rewrites workspace paths to the dashboard's viewer. Acceptance criteria name the repository's functional tests and checks, not workflow-owned steps; `test-rules-review`, review summaries, commit, finalize, and rebase belong to review or completion, and the generated plan ends with implementation and the execution report.

### Pilot stop

In any supervised phase, the pilot may decide `stop` with a reason. The daemon records `pilot_stop` on the flight (phase, reason, source turn, time) and a `pilot_stop` message in monitor history, and does nothing else: no chat message, cancellation, interruption, hidden control, or disabled action. Sessions keep running, later turns keep notifying, and every phase action stays offered. The list's activity line and the detail page lead with "Pilot stopped: <reason>" until the phase changes; the payload exposes `pilot_stop` only while the flight is in the phase the stop was made in. The user reads the reason and decides.

### Completion

**Review and commit** is offered on a `reviewing` flight, whatever the reviewer reported, whether a summary exists, and whether a stop is recorded; an `executing` flight no longer offers it (the edit form's stage field remains the escape hatch). It is the flight's one human review-and-commit checkpoint: clicking it is the user's approval of the work, and no other action approves anything. It spawns the **committer** with the executor's model under the `commit` role, records on the completion operation which reviewer was current (a `reviewer` resource), and moves the flight to `completing`. The committer's prompt (`CommitterPrompt`) says the user approved the work, then: stage every change except `review/`, including the spec and plan at their exact paths, and invoke the repository's commit skill, running its gates once per attempt; on a gate failure stop and report the actual output, without rerunning gates, changing the work, reverting, or starting or killing a suite; if the work changed after the user approved it, because a reviewer repaired something, ask the user in the conversation to approve the repaired work and wait for their answer, and never treat a message from the pilot as the user's approval; only after the work commit succeeds remove `review/`; run `/finalize --amend --commit <hash> --spec <spec_path> --plan <plan_path>`; amend the work commit with the finalize changes without rerunning gates; report the final hash and files; never rebase or push. The repository's `finalize` and `commit` skills (`.agents/skills/`) have an explicit amend mode for this: finalize processes only the named documents, makes the standard consolidation choices without asking, and amends the named commit through `/commit --amend`, which keeps the message and skips the gates.

While the flight is `completing`, every committer turn notifies the pilot with the `commit` classifiers' answers and the commit job: check the response against the workspace, route a gate failure to a fresh reviewer with `next_reviewer` carrying the failure, and let the committer retry only after a reviewer changes nothing and everything it checked passed and the user has approved the repaired work again. Guidance may go to any started session, `"to": "commit"` or `"to": "reviewer"` in practice. The assigned reviewer is followed and notifies on every turn while completing, whether it reviewed the work before completion or was started after a gate failed. Nothing is terminated or unstaged by the daemon. Completing is the last phase; nothing follows it but dispose. Rebase, push, and merge are the user's.

Configure flight naming and the TypeSafe API key under **Settings → Flights**.
The Flights page's **Settings** link opens this tab. The key is in **Pilot Supervision**.
Set, update, and removal use the standard password prompt and config-update API;
only the presence of a stored key is returned to the browser. The key is saved in
`secrets.json` under `providers.typesafe.TYPESAFE_API_KEY`, using the same owner-only,
atomic secret-file storage as other providers. It is read for each classification,
so changes apply without restarting the daemon. Removing the stored key leaves
classification unconfigured. Existing failed turns can be retried from monitor history.
A missing key is a visible classification failure, not a routine ruling. Neither
Claude nor the TypeSafe Claude skill sits in the production classification path.

The Flights page displays a warning above the list and forms when the daemon
cannot resolve the TypeSafe API key. The warning
links to the Flights settings tab. This check comes from GET `/api/config`
and uses the same configured provider secret as classification.
The local readiness check does not call Jev or verify the key with the provider.

## Architecture decisions

- **Sole-writer rule.** `flights.Manager` is the only writer of `~/.schmux/flights.json`. Handlers, transition functions, and the persistence layer never edit flight state directly — they call into the manager and serialize the resulting snapshot atomically (`internal/flights/manager.go:108`). A pending `Operation` is persisted before any external call, then re-persisted with its outcome, so a daemon crash leaves a visible attempt.
- **Superseded: manual workflow.** No session signal, chat activity, transcript assessment, or elapsed time advances a flight, and the daemon never judges readiness: the pilot does, from the evidence, with an explicit advance decision. The manual phase actions remain available as overrides. The `Spec:`/`Plan:` report is information for the executor's and reviewer's prompts, never a gate: Enter execution does not require a verified report and rechecks nothing (an earlier build returned 409 without one; the user rejected that on 2026-10-25 and again on 2026-10-28: parsing to retrieve information is in line with the approach, blocking the user on it is not). Schmux never inspects planning quality. Execution supervision records skill use and report evidence for the pilot and the user, but a verified report or a classifier answer never advances the flight on its own.
- **Human review belongs with the commit, not with every phase.** The pilot advances `planning → executing` and `executing → reviewing` on its own explicit decision; the user reviews the work, the artifacts, and the running changes once, at the commit, where the existing completion action is presented as **Review and commit**. Four choices carry that: an explicit `advance` decision form rather than an inferred one, reuse of the existing `EnterExecution`/`EnterReview` transitions rather than a parallel path, the human checkpoint placed on the existing completion action rather than a new approval page, and no automation toggle, per-flight switch, or configurable phase graph — this is the ordinary workflow, not an optional mode. Dropping the intermediate approvals does not authorize guessing an unresolved requirement or answering a native permission card.
- **The renewed human approval a repair needs is prompt-level, not enforced.** A committer whose work changed after the user approved it must ask in the chat and wait for the user's answer; that rule lives in `CommitterPrompt` and in the committer's pilot job, because the daemon cannot tell a pilot's message from the user's. The same holds for the pilot's judgment of readiness: the daemon applies an explicit decision and never evaluates readiness itself.
- **The skills choose where the spec and plan go.** Schmux never dictates a location. It tells the planner to let `superpowers:brainstorming` and `superpowers:writing-plans` place the documents and to report the absolute paths, then deterministically checks each report and surfaces any violation in the monitor history and the pilot's notification.
- **One pilot supervises every working role.** There is no second pilot. `monitoredSessions` (`internal/flights/monitor.go`) follows every session the flight has started, in every supervised phase, and a pilot decision may address any of them by role, never by session ID; the daemon resolves the role to the flight's currently assigned session, and a decision error is a visible error on the turn, nothing more. An earlier build followed and let the pilot address only the current phase's worker; it was removed on 2026-10-27 because an orchestrator must be able to reach, and hear from, every session it is responsible for (the planner during execution, the pre-completion reviewer during completion). Which turns wake the pilot is still decided per turn: the phase's own worker on every turn, everyone else through the classifiers.
- **Only the verified report proves execution finished.** A Jev answer, an `execution_state: finished` classification, and the executor's own claim are all not proof. The report counts only as a regular, nonempty file inside the workspace modified after execution started; the first turn whose check passes sets the flight's `report_path`.
- **Every executor turn notifies the pilot, whatever the classifiers say.** A failed classification still notifies, with the classification error in place of answers: most executions end in one turn, and a classifier that hid an ordinary-looking turn would leave the one turn most executions produce unwatched. `notify_on` and `min_confidence` decide the pilot's planning turns only.
- **A fresh reviewer, not the planner, reviews the work.** The planner's conversation is biased toward its own plan being right, so the planner does not check executed work and has no `work_check` classifier. Each reviewer starts with no shared history; after a reviewer changes anything, the pilot asks for another, and the chain converges when one changes nothing and everything it checked passed. The superseded reviewer is left running, untouched.
- **Review and completion read nothing from the workspace.** The daemon runs no tests, reads no spec, plan, report, or test file, checks no file's existence, and parses no structured line from a reviewer or committer response. The review reading is Jev's classification of the response, shown in words; the skill check reads only the session's own chat records. No classification, missing artifact, or pilot stop blocks Review and commit or dispose.
- **The pilot is an orchestrator, not a responder.** Every completed pilot response is read for a decision, whatever prompted it, and a decision is never tied to a notification. An earlier build read only responses to messages schmux had sent (first by a copied `notification_id`, then by the chat input the turn answered) and rejected the rest; it was removed because it blocked the pilot from acting on the user's instructions and stalled a flight when a `next_reviewer` named an executor notification during review. Prose is the pilot talking to the user and is not an error.
- **Schmux does not answer a decision error back to the pilot.** A decision error (wrong recipient, malformed JSON, a failed spawn) is recorded on the pilot's turn and shown on the flight; nothing is sent to the pilot. A definite delivery failure of a valid message is not a decision error: the sender is told `Your message to <recipient> was not delivered: <send error>.` (see "Undelivered messages"). Builds before 2026-10-28 sent the error back as a `rejection` message so the pilot could "answer again", bounded to one per decision. The user asked for that retry loop to go on 2026-10-27, with the rest of the request/response design: schmux tells the pilot what happened and carries out its decisions, it does not negotiate with it. The `rejection` message kind stays loadable as history.
- **A message that definitely failed to send is answered to its sender.** An agent that sends a flight message and hears nothing cannot tell a lost message from a delivered one, so a definite send failure produces one plain-text notification to the original sender: `Your message to <recipient> was not delivered: <send error>.` The rule is agent-agnostic: the sender and the recipient are the session IDs already on the message, and neither role is special-cased. A role-specific design — answer only the pilot, naming the role it addressed — was proposed first and superseded. Only a definite failure notifies: an ambiguous outcome (status `unknown`, a send interrupted by daemon shutdown) may have been delivered, so it is never reported as a failure and the message is not resent. A validation error is not a delivery failure and stays silent. Nothing else changes: no retry, no new message kind, no persisted state, no API contract, no dashboard.
- **There is no done state.** Completing is the last phase. The stage-1 build had a "Mark done" button and a `done` state as a placeholder for the unbuilt rebase, push, and merge steps; the user never asked for them, and they were removed on 2026-10-28. A flight stays in `completing`, owning its workspace and sessions and still supervised, until the user disposes it. `loadSnapshot` maps a recorded `done` state to `completing`; a recorded `done` operation stays in history (`ActionDone` is valid but never written).
- **A stop records and shows; it does nothing else.** A pilot `stop` is a flight field and a monitor-history message. Nothing is cancelled, interrupted, hidden, or disabled; the user decides what to do.
- **Two independent state axes.** `WorkflowState` is the stage axis (`backlog`/`planning`/`executing`/`reviewing`/`completing`). `CleanupState` is the destructive-cleanup axis (`idle`/`disposing`). A `completing` workflow with `disposing` cleanup is valid and retryable. `requireIdle` rejects transitions while cleanup is in flight (`internal/flights/transitions.go:87`).
- **Workspace allocation belongs to takeoff.** A backlog takeoff calls `workspace.Manager.GetOrCreateWithLabel`. Planning does not offer takeoff again; a failed spawn or missing resource stays visible without respawning sessions or reallocating a workspace.
- **Branch name from the prompt.** The first takeoff of a Git flight asks the branch-suggestion feature for a name derived from the flight prompt — the same feature the spawn form uses — and requests that branch from the workspace manager. Takeoff no longer hard-codes `schmux/flight/<flight-id>`: a name like `schmux/flight/fl-a7f37838` says nothing about the work. No name (suggestion not configured, the call failing, an invalid name) fails the takeoff and leaves the flight in `backlog` with no workspace assignment. A backlog flight with a recorded assignment requests the recorded `RequestedBranch` again instead of a new name, so a flight that took off before this change keeps its branch and no migration exists. Sapling flights request no branch and pass the flight display name as the label.
- **Per-flight op-lock, no global lock during external calls.** `flights.Manager.mu` is held only across in-memory edits and persistence. The slow `SpawnLocal` and `DisposeAll` calls run under a per-flight mutex from `opLocks`, so two transitions on the same flight never interleave while two transitions on different flights never contend.
- **One cleanup path.** `disposal.Service.DisposeAll` is the only place that sequences workspace disposal. Dashboard `dispose-all` and flight `dispose` both call it; neither holds its own copy. Force-purge semantics come from exposing `workspace.Manager.DisposeForcePurge` rather than reimplementing filesystem deletion. Remote refs are never modified.
- **One local spawn path.** `spawnlaunch.Launcher` validates the target, checks chat-capability, resolves fence, resolves persona/style context, calls `session.Manager.Spawn`, writes a spawn log, and broadcasts on success. The dashboard's multi-target `/api/spawn` handler and `flights.Manager.Takeoff`/`EnterExecution`/`EnterReview`/`EnterCompletion` and the next-reviewer spawn all use it.
- **Delimited original prompt.** The planner/executor prompts reproduce the original flight prompt byte-for-byte between `----- BEGIN/END ORIGINAL PROMPT -----` markers (`internal/flights/prompts.go:8`) so the flight operator can review the exact wording without diffing composited instructions.
- **No new event channel.** The existing `/ws/dashboard` payload gains a full `flights` array on its initial and debounced snapshots. Clients replace the array from every payload; they never poll. The detail route refetches after a reconnect broadcast that mentions its flight. The list's activity line reads `sessionsById` from the same `SessionsContext`; no polling, no second channel.
- **Dispose confirmation matches workspace ID.** `POST /api/flights/{flightID}/dispose` requires the body's `workspace_id` to match the flight's recorded workspace; a mismatch returns 409 and performs no cleanup. The dashboard consequence modal names the workspace and everything destruction will take (`FlightDisposeModal.tsx`). A flight with no workspace removes at once with a plain Remove confirm.
- **Dispose is the only removal.** Dispose is the sole removal action; there is no separate cancellation state or record-only deletion: the flight record always leaves the list when its resources do, or, when there are no resources, immediately. No path may orphan a workspace from its flight or vice versa; the dashboard's `DELETE /api/flights/{id}` route is unregistered for the same reason.
- **Daemon-generated names.** A flight's `short_name` is written only by the background namer (`internal/flights/naming.go`) through the `flight-name` oneshot (`internal/flightname`); create and update requests no longer carry it. Users never type a name, and creating or editing a flight never waits on the LLM. A flight with empty `name_prompt` is a placeholder — every flight that predates the namer, or was created while naming was off — and is named on the next pass once `flight_name.target` is set, so no migration code exists.
- **Rename on 5% drift from `name_prompt`, not from the last edit.** `promptChange(name_prompt, prompt) >= renameThreshold` (rune Levenshtein divided by the longer string). Comparing against the prompt the current name came from makes many small edits that add up to a real change still trigger a rename, while a typo fix never does.
- **Stale results are dropped, not merged.** The pass snapshots the prompt, calls the LLM outside every manager lock and the per-flight op-lock (so a takeoff never waits on naming), then writes only if the prompt still matches the snapshot. A changed prompt or a disposed flight discards the result; the next pass picks it up.
- **Naming failures live in `name_error`, not `Operations`.** Operations are workflow transitions and `LastError` is derived from them; mixing naming failures in would muddy both. Retries back off 1m → 1h per flight in memory only (`nextBackoff`); a success, a prompt change, or a daemon restart starts the backoff over. An identical repeated error does not rewrite `flights.json` or broadcast.
- **No model means naming is off, not an error.** An empty `flight_name.target` yields `ErrNamingOff`: no `name_error`, no backoff, the ID label stays. There is deliberately no fallback to `branch_suggest` targets. A configured target that doesn't resolve (`ErrTargetNotFound`) is a real failure and shows as `name_error`. A name the model returns that breaks a rule (empty, control characters, 10 or more words, over 80 characters) is `ErrInvalidName`; its `name_error` states the broken rule and quotes the rejected name. Names are not required to be unique.

## Design history

- **Undelivered agent-to-agent messages are answered to the sender, 2026-10-29.** The user's report: the pilot kept addressing an agent that was no longer available, and the guidance went nowhere with no word back. The first design was role-specific — reply to the pilot with `Your guidance to <role> was not delivered: <reason>.` — and it was superseded by the agent-agnostic rule that lives now: any agent sender is told, in the same words, with the recipient session ID and the error the send returned. The rule sits in the existing send path, so it costs no message kind, no persisted state, and no UI. The superseded design is kept as prior work in `docs/superpowers/specs/2026-10-28-pilot-undelivered-reply-design.md`.

- **The flight branch comes from the flight prompt, 2026-10-28.** Takeoff stopped hard-coding `schmux/flight/<flight-id>`. The user's decisions: the name is generated at takeoff and is not shown or editable before it, so no dashboard UI changed; no name fails the takeoff and leaves the flight in `backlog` with no workspace assignment; a flight with a recorded assignment reuses its recorded branch, so flights that already took off need no migration; no new branch-collision logic, because the workspace manager already resolves collisions; and flight disposal deletes that branch whatever its name, under the safety rules it already had.

- **Automatic phase advancement, 2026-10-28.** The user asked that a flight move through planning, execution, and agent review without a click at each phase, with the human's review happening once, at the commit. The increment reused the existing transitions behind an explicit pilot decision rather than adding a scheduler, and it moved the planner's intermediate artifact-approval requirement to the commit so removing the phase clicks did not leave the planner waiting on a sign-off it could never get. A feasibility spike answered the one blocking question — the daemon can advance planning → execution → review with the existing manager methods, four sessions, no committer — and proved only transition reuse, never a live model's readiness judgment. Live acceptance on a real flight, with both Claude and Codex working targets, is still pending.

- **Two classifier questions over one combined ruling.** The `flight-monitor.yaml` definitions ship `attention` and `planning_artifacts` as separate Choice questions over the same planner turn. Each has its own `notify_on` and `min_confidence`, so a turn can require attention and still claim a planning artifact is ready without forcing the observations into one exclusive classification. The YAML choice order is preserved on every Jev request — feasibility runs found that reordering choices could change the model's answers.
- **Takeoff is one-shot by user decision.** A planning flight does not gain a second takeoff after a spawn failure, session loss, or workspace loss; partial outcomes remain visible. An earlier takeoff-retry feature was removed at the user's request because the supervisor flow already covers the recovery surface.
- **Deliberately excluded scope.** Permission answers and native questions stay human-answered; nothing schedules a phase change, and no timer or service advances one. The only automatic advances are the pilot's own two decisions, `planning → executing` and `executing → reviewing`; takeoff, completion, rebase, push, merge, and disposal stay the user's. Execution supervision runs at turn boundaries only: it does not stop a commit or a subagent dispatch as it happens. Restarting execution, wiping the workspace, capturing a baseline, a follow-up plan or second executor, routing the user's hands-on feedback back into the flight, terminating or unstaging a failed committer, disposing or messaging a superseded reviewer, counting stops or reviewers across flights, checking that brainstorming ran during planning, rebase, push, and migrating flights recorded by earlier builds are not built. Pilot guidance is delivered as ordinary chat input and may queue behind a native permission card that the user must resolve manually. "I want to get from soup to nuts for a flight, and then we can start to figure out nuance and complexity" (2026-10-24).
- **Why review and completion are phases.** Before them a flight ended at `executing`, and the retained chat history (214 conversations, 2026-09-23 to 2026-10-26) showed that the stretch from the agent's "done" to the commit was where the user's time went: telling the agent to fix what its own review found, typing `/test-rules-review` and "fix" in rounds, asking whether the tests actually ran, asking for the handoff and for artifacts to be moved into `review/`, and catching untrue claims; then, at commit time, committers rerunning gates, gates hanging, committers changing the work, and `/finalize` and `/rebase` typed by hand. The one automated flight that reached review before this build (`fl-29a54794`, 2026-10-24) did the review work well with one click and one pilot correction; that build was wiped because its daemon parsed `Test:` lines, computed freshness from file edits, and blocked Enter review on them. The review workflow worked; the enforcement around it did not, which is why review and completion read nothing from the workspace and gate nothing. The user's decisions behind the design, with dates: review is a phase like planning and execution, started and ended by the user (2026-10-24); a fresh reviewer with the planner's model does the review, not the planner, and another follows every fix (2026-10-26, replacing the 2026-10-24 decision that the planner reviews); fix in place, no wipe or redo (2026-10-24); the pilot may say the work has gone off the rails and "stop means stop", with no interrupt or cancellation (2026-10-24/25); nothing blocks the user, who may still force a phase (2026-10-25); the agents prove they did their job, so tests and `test-rules-review` run and run again after fixes (2026-10-24); `test-rules-review` is part of review and `spec-coherence-check` is not (2026-10-24); acceptance criteria are written in the spec during planning, in the industry's ordinary sense (2026-10-24/26); artifacts need not be fresh (2026-10-24); how complete testing is defined is the repository's convention, not schmux's (2026-10-25); `review/` is where artifacts go and it is not git-ignored, so the dashboard can open them (2026-10-25); fix loops should be bounded, but the user does not know how, so nothing caps them yet (2026-10-25); the commit must not contain `review/`, cleanup waits for commit success, finalize is amended onto the work commit, and rebase is exclusively a user action (2026-10-25/26).
- **Review and completion acceptance is pending on a real flight.** The increment's fifteen acceptance criteria (Enter review spawns a fresh reviewer with the planner's model and the prompt above; a reviewer that changed something is followed by another; a stop shows and disables nothing; Review and commit is offered whatever was reported; the committer's commit contains no `review/`, spec, or plan file but does contain the finalize changes; a failed gate is run once and routed through a fresh reviewer; only Dispose remains on `completing`; all of it with both a Claude and a Codex planner target) are covered by unit, handler, and scenario tests (`test/scenarios/flights-review-completion.md`) but have not been checked end to end on a real repository.
- **The question set is part of the workflow, not user configuration.** The workflow is not something each user designs, so the classifier definitions ship inside schmux (`internal/flights/flight-monitor.yaml`, embedded) rather than being installed into `~/.schmux` for users to edit. An earlier build installed and read a per-user copy; that file is no longer read. Schemas and routing live in the file; the Go engine only knows Choice questions and `notify_on` semantics. Adding another Choice question of that shape needs no Go change.
- **Classification independence from agent harnesses.** The direct Jev HTTP request sits in `internal/flights/monitor_jev.go` with keyed question/criterion objects and bearer auth; Claude and the TypeSafe Claude skill are not in the production path. Classifier feasibility evidence came from an out-of-repo Jev spike against real final assistant messages; the live classifier's accuracy on the four backlog flights is pending manual acceptance, so unit tests prove transport and recovery, not accuracy.
- **The skill check can only be as strong as the harness allows.** Claude invokes a skill through a `Skill` tool call; Codex has no skill tool and reads `SKILL.md` with a shell command, recorded as a `commandExecution` item. For Codex the check can therefore only show that the skill file was read, and its text says which kind of evidence it found: `executing-plans invoked at record N`, `executing-plans skill file read at record N`, or `executing-plans not found`.
- **Forbidden behavior does happen, so supervision runs at turn boundaries only.** Of the 36 retained executions examined for the design, 1 ran `git commit` and 4 dispatched an `Agent`, and 28 ended in a single completed turn. Both numbers shaped the increment: the executor's prohibitions stay prompt instructions (only actual skill use is checked), and every executor turn notifies the pilot regardless of its classifiers.

## Gotchas

- **A malformed snapshot disables flights, not the daemon.** An unreadable or malformed `flights.json` is logged (`continuing without flights`), flight endpoints return 503, and sessions and workspaces remain available; no manager is exposed for writes and the file is never rewritten or repaired.
- **An invalid flight row is quarantined, not fatal.** A row that fails to decode or validate (an unknown state, role, action, or status; a duplicate ID; inconsistent monitor records or a pilot stop that names a missing turn) is kept aside as raw JSON (`Manager.invalidFlights`), left out of the list and the dashboard, and written back unchanged on the next save, so a newer build's data is never dropped. Unknown fields on valid rows round-trip the same way. There is no UI for quarantined rows; the daemon log is the only trace.
- **An edit refuses to overwrite a file that changed on disk.** `edit()` fingerprints the snapshot it loaded and returns 409 `flights snapshot changed on disk; reload schmux before editing` when `flights.json` no longer matches, so a hand edit or a second daemon is never silently clobbered.

- **A flight's resources include any session in the workspace.** `dispose` enumerates sessions live in the workspace at call time, not only the planner/executor/commit assignments. Other sessions stored under the same workspace ID that belong to a different flight are left in place.
- **Chat history is deleted only by dispose.** Ordinary `dispose-all` keeps the conversation record (default retention). Dispose passes `ChatSessionIDs` (recorded current + prior IDs) plus live-workspace sessions into `disposal.Service`, which calls `chat.DeleteConversations` only when that list is non-empty.
- **Force-purge rejects on stuck sessions.** `disposal.Service` calls `Workspaces.DisposeForcePurge` only after every session dispose succeeds; otherwise it reverts the workspace status and returns the session errors joined. A live session is never left behind a purged workspace.
- **Workspace dispose-guard rails are bypassed by force-purge.** Uncommitted changes, unpushed commits, and recycling all lose to `DisposeForcePurge`. The flight branch is removed at the end via `Workspaces.CleanupFlightBranch` only when no other worktree still references it; remote refs are never touched.
- **Flight branch cleanup has one caller.** `workspace.Manager.CleanupFlightBranch` is reached only from `disposal.Service.DisposeAll`, and only for a force purge whose request carries a branch name. Only flight disposal sets that field, so the branch it deletes is always the one the flight recorded.
- **Restart preserves the `disposing` state.** Daemon restart leaves cleanup-state and recorded outcomes intact; an incomplete dispose can be retried explicitly. Already-absent resources count as cleaned.
- **The flight edit form lets the user pick a non-listed value.** Every recorded field (including planner/executor models) is editable in every stage; a value that has since been removed from config stays selectable on the flight that recorded it (`FlightEditForm.tsx`).
- **Stage is editable directly.** Saving a new `workflow_state` does not run a transition; it only writes the field. To advance, click the action button or let the pilot advance it. The edit opens a new phase visit, and it is refused while a transition operation is pending.
- **A pilot turn's visit comes from the harness's start record, not from when the daemon noticed it.** `PlannerTurn.StartedAt` is read from the harness's own root-start record — a Claude dispatch marker or a Codex `turn/started` — and fallback assistant traffic invents none. A turn is bound to the current visit only when it began strictly after the visit began and not later than the moment the daemon retained it; a start at the boundary, before it, or after the observation binds to no visit. A turn with no visit can never advance a phase: it stays visible history that guidance can still use.
- **A direct stage edit opens a new phase visit.** The edit goes through the same setter as the transitions, so editing a flight away from a phase and back makes the earlier pilot turn stale — it cannot advance the phase the flight came back to. This is deliberate: the phase the pilot judged is not the phase the flight is in.
- **A visit's clock must move forward.** A phase entered with a clock that does not advance past the last known boundary is recorded with `phase_time_uncertain` and binds no turns, so nothing advances the flight automatically. The boundary is retained across edits and daemon restarts, and only a later phase entry with a strictly newer timestamp restores eligibility. Manual actions stay available.
- **Only a definite failure is retryable.** A spawn that failed definitely leaves the source phase and a failed operation the user may retry. A spawn whose outcome cannot be established leaves the operation pending, and a pending operation is never retried automatically: the retry could start a second session for an outcome nobody knows.
- **The committer starting is not commit success.** The dashboard shows the phase and the last error; it never infers approval or merge readiness from the phase alone, and a failed finalize is not ready to merge.
- **Workspace header flight button is conditional.** It appears only when the current workspace appears in the derived `flightByWorkspaceId` map (recorded assignments, not lifecycle hints). Unassigned workspaces render no flight control — there is no "create flight for this workspace" button on the header.
- **`order` is meaningful only in backlog.** Section membership and manual ordering use `workflow_state`, including backlog flights that retain a workspace after editing. `POST /api/flights/order` requires every backlog ID and rejects flights in another workflow state. Started flights use session activity order.
- **Activity line uses the sidebar's adjusted timestamp rule.** The list ranks started flights by `last_output_at` minus one hour when the session is in progress, exactly as `lib/workspaceSort.ts:24` does for the sidebar workspace time sort. The shared `sessionActivityTime`/`latestActivityTime` helpers in `workspaceSort.ts` are the single source. `flightActivity` also records the in-progress result, and the line reads "Working" from it, so the wording and the order agree. A resolved session with no output yet still gets a linked line; "session gone" means no role session resolved at all.
- **One status line per started row.** The line combines the recorded stage, selected role, observed session state, and relative output time. Cleanup replaces it with "Disposing"; otherwise a pilot stop replaces it with "Pilot stopped: <reason>", and on the list a review reading replaces it with "Reviewer reports: …" (the detail page shows the reading in its own row); no assignments renders `<Stage> · No session`. In a tie on activity time the line names the role the current phase supervises. There are no list status pills or resource stacks. The flight name opens the resource inventory on the detail page. Section headers explain manual backlog order and the adjusted activity order.
- **Sapling workspace labels are fixed at takeoff.** Takeoff sets the workspace label from the flight's `short_name` at that moment (`internal/flights/transitions.go:328-330`, `displayName`). Git repos get the branch suggested from the prompt and no label. A later rename does not relabel a Sapling workspace; the dashboard surfaces the current name via `flightLabel` everywhere else.
- **`RequestedBranch` is the name asked for; `Branch` is the name the manager returned.** The workspace manager suffixes a requested branch when another worktree has it checked out, so the two differ on a suffixed flight.
- **A suggested branch can collide, and the workspace manager decides.** `GetOrCreateWithLabel` reuses a matching idle workspace, checks out an existing branch, suffixes a branch another worktree has checked out, or fails with a namespace-conflict error. A conflict leaves the flight in `backlog`, exactly as any workspace-allocation failure does.
- **The suggestion call can hold a takeoff for 30 seconds.** `branchsuggest` caps its oneshot at 30s, and takeoff holds the flight's op-lock across it, so a slow suggestion delays that one flight and nothing else.
- **A nil branch suggester is a disabled suggestion.** `flights.Manager` treats a nil `Dependencies.Branches` as `oneshot.ErrDisabled`, so a manager built without one cannot take a flight off.
- **`StartNaming` must run after `wireCallbacks`.** The oneshot path resolves targets through the model manager that `wireCallbacks` installs (`oneshot.SetModelManager`, `models.SetDefault`). Starting the namer earlier makes the first pass report every placeholder as "model not found"; `Run` starts it right after `wireCallbacks` (`internal/daemon/daemon.go:479`).
- **`short_name` in a request is silently ignored.** The flight handlers don't use `DisallowUnknownFields`, so an old client sending `short_name` gets a 200 and no change.
- **`name_error` shows only on the list rows and the detail page.** The workspace header button and toasts show `flightLabel` alone.
- **A waiting session is not "in progress", so the activity line needs its own rule.** A pending question or permission sets the chat session's nudge state to "Needs Input", which `isSessionInProgress` (`assets/dashboard/src/lib/workspaceSort.ts`) does not count as in progress. Without a flights-specific rule a waiting executor is hidden whenever the planner spoke more recently. `flightActivity` (`assets/dashboard/src/lib/flights.ts`) prefers a "Needs Input" session, and `useFlightInProgress` keeps the list and the detail page on one predicate. The shared in-progress check and the sidebar workspace sort are unchanged.
- **The executor's prohibitions are not enforced.** "No subagents, no commits, skip `superpowers:finishing-a-development-branch`" is prompt text. Only actual use of the execution skill is checked, and only at turn boundaries; nothing stops a commit or a subagent dispatch mid-turn.
- **A delivery-failure notice shares its source turn with the message it reports.** `recordFlightMessage` drops any message whose `(SourceTurnID, Kind)` already exists, and the notice reuses kind `notification` with the failed message's own source turn. A message sent by a working session therefore loses its notice whenever the monitor already recorded a notification for that same turn — which it does for every turn it finds interesting. Today only the pilot sends messages, and the monitor never notifies for a pilot turn, so the collision cannot happen; the first working session that sends a message will hit it, and the fix is a source turn that identifies the failed message rather than the turn that produced it.
- **`[Pilot]` attribution follows the message kind, not the sender.** The prefix is added when `msg.Kind == "pilot_message"`, so a working session's message of that kind still reaches the recipient as pilot guidance.

## Common modification patterns

- **Add a new transition.** Add an `OperationAction` constant in `internal/flights/model.go`, a `(m *Manager) <Name>(ctx, id)` in `transitions.go`, a HTTP handler in `internal/dashboard/handlers_flights.go`, a route in `registerMutatingRoutes`, a typed client function in `assets/dashboard/src/lib/api.ts`, a button in `FlightActions.tsx`, and an `Action`→`label` mapping in `assets/dashboard/src/lib/flights.ts`. Persist a pending `Operation` before any external call, then its outcome. Create it through `begin`, which also enforces the shared pending-transition guard; a transition whose outcome cannot be persisted leaves its operation pending, naming it, for the user to reconcile.
- **Add a pilot decision form.** Add a `json.RawMessage` field to `pilotDecision` in `internal/flights/pilot.go`, a `form…` constant, the field to the "exactly one of" count and to the dispatch switch in `recordPilotGuidance`, and the form to the contract text in `internal/flights/prompts.go` (`decisionContract` and `PilotPrompt`) and to `pilotJobForRole` wherever the responsibilities are restated. Assert the form's text by name in `prompts_test.go` and its matrix in `pilot_decision_test.go`.
- **Change what an undelivered message says, or when it is sent.** The wording and the decision to notify live in one place: `recordDeliveryFailureNotice` (`internal/flights/pilot.go`), which records a pending `notification` addressed to the original sender. It is called from the two places a send can fail — `deliverPilotGuidance` (the message never reached the queue) and `deliverFlightMessageLocked` (the send was attempted) — so add a call site rather than a second helper. Keep the notice's `SenderSessionID` empty: a notice has no sender, and that is what stops it from producing a notice of its own.
- **Change the automatic phases.** The two destinations are `advanceDestinations` in `internal/flights/pilot.go`; the phase each one starts from is checked in `advancePilotPhase` and again in the locked transition it calls. A new destination needs a locked transition to call, the shared pending-operation guard, and a story entry that names the deciding turn.
- **Change a role's prompt.** Edit `internal/flights/prompts.go` — keep the `BEGIN ORIGINAL PROMPT` / `END ORIGINAL PROMPT` markers around the user-supplied text so the verbatim contract survives.
- **Add or change a classifier.** Edit `internal/flights/flight-monitor.yaml`: one Choice question per classifier, with its choices, `notify_on`, and `min_confidence`. The `planner`, `executor`, `reviewer`, and `commit` roles are required (`parseMonitorConfig`, `internal/flights/monitor_config.go`), and a test keeps the shipped file valid. The engine supports Choice questions and `notify_on` filtering only, so another question of that shape needs no Go change.
- **Supervise another role.** Add the role to `SessionRole` (`internal/flights/model.go`), give it classifiers in `flight-monitor.yaml`, list it in `monitoredSessions`, `notifiesEveryTurn`, `pilotJobForRole`, and the per-role check dispatch in `processMonitorWork` (`internal/flights/monitor.go`), add it to `pilotRecipientRoles` (`internal/flights/pilot.go`) — `deliverFlightMessageLocked` resolves the sender and recipient roles from the flight's session assignments, so an assigned role is addressable as soon as it is assigned — and to the role switch in `buildJevRequest` (`internal/flights/monitor_jev.go`), and add its label to `ROLE_LABEL` (`assets/dashboard/src/lib/flights.ts`).
- **Add a resource step to dispose.** Extend `disposal.Service.Request` for any workspace-wide step that the dashboard dispose-all path should also gain (force-purge and chat-delete already are), or pass `Observe func(ResourceOutcome)` per call if the step is flight-only. Keep remote-branch ops behind the caller's `ctx`; everything else runs on an independent context so HTTP client disconnects don't abort cleanup.
- **Expose a new flight field on the dashboard.** Add it to `contracts.FlightDetailResponse` and `contracts.FlightSummaryResponse` in `internal/api/contracts/flights.go`, run `go run ./cmd/gen-types`, render it in `FlightDetailPage.tsx` or the relevant list column. Never edit `types.generated.ts` by hand.
- **Change how names are written.** Prompt wording and the name rules (fewer than 10 words, ≤80 runes, no control characters) live in `internal/flightname/flightname.go` (`Prompt`, `validateName`). The rename threshold, tick, and backoff cap are `renameThreshold`, `namingTick`, and `maxNamingBackoff` in `internal/flights/naming.go`; tests drive `runNamingPass` directly with a `fakeNamer` and a settable clock.
- **Change how a flight names its branch.** The seam is `flights.BranchSuggester` (`internal/flights/manager.go`), called from `Manager.suggestBranch` (`internal/flights/transitions.go`); the daemon's implementation `flightBranchSuggester` (`internal/daemon/flights.go`) calls `branchsuggest.AskForPrompt`. The prompt and the rules the returned name must satisfy live in `internal/branchsuggest/branchsuggest.go` (`Prompt`, `validateSuggestedBranch`), and the spawn form makes the same call — changing the wording changes both the spawn form and flight takeoff.
- **Move a workspace to a different flight.** Don't. A flight's `WorkspaceAssignment` is recorded at takeoff; replacing it would let dispose clean the wrong workspace. Add a new flight instead.
