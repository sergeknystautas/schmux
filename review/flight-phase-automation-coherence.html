Findings and corrections

Finding Evidence and correction
State ownership and stale decisions were underspecified. internal/flights/manager.go:327 allows direct stage edits, while :451 owns persist-before-notify. The spec now names Manager as the single owner, includes direct edits in phase-entry tracking, defines a phase visit, and binds decisions to their turn-start visit. Stops no longer reactivate merely because a flight returns to the same phase. Spec lines 110 and 116.
Manual overrides conflicted with protection against duplicate spawns after uncertain outcomes. internal/flights/transitions.go:87 checks cleanup only; :105 records a pending operation. The spec now requires pending-operation protection in the shared transition path, applying to manual and automatic entry points. Stage edits cannot bypass it. Manual overrides continue to override readiness judgments and pilot stops. Spec lines 79 and 124.
Required story provenance had optional API scope and omitted its presentation owner. assets/dashboard/src/lib/flightStory.ts:122 builds operation entries; internal/api/contracts/flights.go:74 defines their API data. The spec now requires provenance in contracts/projections, names the story builder, and specifies consistent list/detail meanings and centralized action labels. Spec lines 134 and 147–148.
The repair approval rule was described as retaining current retry behavior. internal/flights/monitor.go:478 allows retry after a clean reviewer without naming renewed human approval. The spec now explicitly identifies the additional prompt-level condition and requires consistent updates to the pilot's commit job and committer prompt. It retains the clean-review condition and does not claim mechanical approval enforcement. Spec line 87.

Procedure results

  • Contradictions: checked workflow, decision validation, manual overrides, recovery, and all twelve acceptance criteria. The corrections above align the requirements.
  • Scope: pilot parsing and prompts own the new action; shared transitions and Manager own mutations; turn retention and persistence support replay protection; contracts and the existing story expose provenance; tests and documentation follow those changes. No new service, dependency, scheduler, or workflow framework is proposed. A line-count estimate was not produced.
  • Terminology: backlog, planning, executing, reviewing, completing, pilot, planner, executor, reviewer, committer, operation, turn, and story match existing code vocabulary. “Advance” is explicitly introduced as a decision form; “phase visit” is now defined; “Review and commit” is explicitly a label for the existing completion action.
  • Goal alignment: the pilot chooses advancement and the daemon executes its decision. Routine phase approvals disappear; the human reviews at commit time. Actual questions, failures, and stops remain interruptions. Renewed approval after a repair is an exceptional prompt-level condition, not a second normal-path checkpoint.
  • Views: the detail view owns actions and history; the list keeps its activity/review reading and detail links. Neither derives human approval or commit success from phase alone. Shared labels remain centralized.
  • Ownership: Manager owns persisted flight state; the pilot requests mutations; the dashboard displays notifications after persistence. No parallel state writer is proposed.

Limits

No production code or tests were changed. No runtime tests, lint, typecheck, live-model check, or implementation gate was run for this review. The earlier throwaway spike proves reuse of existing transitions only. Recovery behavior, pilot judgment, and prompt-level approval behavior still require implementation validation.
