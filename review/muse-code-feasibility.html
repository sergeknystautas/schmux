28 September 2026 · schmux-002 · Muse Code 1.4.0 (1.4.0-R4302.1)

Muse Code can fit schmux’s native chat architecture

Recommendation: implement native chat with a dedicated Muse Session Protocol adapter and chat reducer. Live probes verified streamed answers, conversational context, questions, approval and denial, interruption, and durable resume. Terminal integration is smaller, but a structured transcript already requires much of the event interpretation needed for chat. No missing Muse capability was found for this core scope.

Model access worked in the investigated environment. After subscription setup and the user’s network exception for api.meta.ai, Muse completed real turns using meta / muse-spark-1.3-contributor. These results validate the Muse protocol; the schmux dashboard integration is still to be implemented.

Project status: deferred. The user is evaluating Muse’s usefulness on real tasks in a normal shell before choosing integration work. The companion draft integration spec preserves the proposed behavior, implementation boundaries, wire examples, open decisions, and acceptance requirements. Neither document is an implementation approval.

What each integration would involve

Format Feasibility and work Assessment
Terminal session A descriptor can detect muse, pass a positional prompt, select --model, and use resume --last or an exact session ID. Verified CLI help matches schmux’s existing argument model. Lifecycle hooks need separate validation for reliable status and captured resume IDs. Low effort for basic launch. TUI inside schmux has not been exercised.
Structured, read-only transcript MSP provides item history and live item events; resumed history was observed locally. A Muse event reducer is still required. This checkout has terminal and chat session kinds, not a generic transcript importer. Feasible. Sensible as an incremental milestone within chat support.
Native chat Run muse serve through schmux’s existing file bridge. Add the Muse handshake, command encoders, session recovery, event reducer, and permission/question mapping. Preferred. Moderate integration work; no transport replacement appears necessary.

Muse’s exec --json is a separate single-prompt surface. Its documented headless mode cannot interactively answer approvals. MSP is the better foundation for a persistent conversation. A separate host cannot simply attach to a TUI’s stdin; retained-session resume must also respect Muse’s writer lease. Headless documentation · MSP transport · Session lifecycle

What was actually verified

Probes used a disposable workspace and newly spawned Muse hosts. Minimal conversation probes disabled shell execution and workspace writes. Tool probes used the default sandbox with promptUnmatched approvals; only the exact requested marker-file command was allowed. No schmux daemon was restarted by the probe. This report preserves the observed outcomes after removal of the disposable client, raw captures, schema export, and marker file.

Where the implementation belongs

Keep the existing Go bridge, conversation record, WebSocket, and chat page. MSP is newline-delimited JSON-RPC over standard input/output. A direct Go protocol implementation fits the current architecture; a Node sidecar and the TypeScript SDK are optional, not required. Wire guide

Code area Necessary addition
internal/detect/ Add a Muse descriptor and allow muse-msp in descriptor.go. Existing runtime YAML overrides can supply terminal launch settings, but cannot implement a new chat protocol.
internal/chat/ Implement and register Protocol in protocol.go: handshake, command IDs, session/turn addressing, sending, stop, decisions, answers, resume, and rebuild after daemon restart. Preserve command IDs during recovery so retries do not duplicate work.
runtime.go, nudge.go Extend control resolution, including extractControlRequestID, and activity/status handling. The existing helpers understand Claude/Codex response shapes; Muse decision commands and resolved notifications have different semantics.
assets/dashboard/src/lib/chat/ Add muse.ts, the protocol union member in types.ts, and reducer/request-resolution dispatchers in reducer.ts. Map text, reasoning, tools, errors, user input and background activity into the existing conversation model.
Permission/question controls Current PermissionCard.tsx accepts a boolean. Muse requires a server-provided choice and current requirement ID. An initial implementation can select offered allow-once/deny choices; complete coverage needs explicit choices and stage updates. Receipt acknowledgements must not dismiss an undecided approval.
Auth, network, workspace Add Muse login/error handling, the evidenced api.meta.ai fence destination, correct workspace instruction handling, and resume behavior. Keep transport/model failures distinct from signed-out errors. Local chat is the existing supported scope; remote chat would be additional work.

MSP item objects have revisions; full updates replace older revisions, while text deltas are temporary and final items carry durable content. This maps well to schmux’s existing live-versus-recorded split. Recovery must still honor cursors, gaps, snapshots, and incomplete items. Tool results in the live captures use visibleOutput. The captures also contain reminderChild items, including a cancelled child in a successfully completed parent turn: parent status must come from the parent lifecycle, not an arbitrary child’s status. Item fold contract

Approvals have presentation receipts, explicit decision commands, staged requirements, and final resolution events. These are materially different from a simple JSON-RPC reply. Resume support also depends on the host’s durability profile: an ephemeral host cannot resume a stored session even if schmux retains the display history. Approval contract · Durability profiles

Scope and remaining uncertainty

Engineering estimate, not a commitment: basic terminal registration is hours of work; a usable local chat integration is several days. Robust approval handling, replay, reconnect, errors, and acceptance coverage could bring the work to roughly one–two engineer-weeks, assuming working inference and a fixed supported Muse version. The task is broader than adding a YAML file, but does not call for a new chat architecture.

Use the installed schema as the implementation reference and record the supported version/fingerprint. The public protocol guide labels the surface pre-1.0, and the online documentation and earlier corpus fingerprints differ from this binary. Similar method names do not make MSP interchangeable with the Codex protocol. Versioning guidance

The feasibility checks have live evidence; model usefulness on real work remains a separate decision. If implementation is chosen, first resolve the draft spec’s open decisions and recapture the relevant exchanges on the supported release. Then validate the integrated dashboard’s rendering, dispatch queue, pending actions, reconnect, daemon reattachment, and native-session Restart. Pending-approval recovery, multi-stage choices, large outputs, and unknown item kinds need explicit coverage.

Preserve three lifecycle distinctions. A browser reconnect restores schmux’s recorded display. A daemon restart reattaches to a Muse process that may still be running in tmux. A session Restart creates a new host that resumes a native conversation. The live probes exercised the native stop/resume cycle needed by the third; none exercised these paths through schmux. Merging returned history with schmux’s seeded history remains implementation work.
