Findings

1. capture-failure-codex.sh can never write a failure event

The script decides failure only when tool_response is an object with a non-zero exit_code or an error field. The implementer's own capture (internal/detect/hooks/README-codex-payloads.md) records that the real payload's tool_response is a string, and the README says so in as many words, then describes the script as handling "that structured form". The tests feed the object form, so they pass while the installed hook does nothing. The plan's instruction was to adjust the script and its tests to what the capture showed.

I traced the shape in the Codex source rather than re-running the probe. For the shell tool, ExecCommandToolOutput::post_tool_use_response (codex-rs/core/src/tools/context.rs) returns JsonValue::String(truncated_output_with_policy(...)): the command's output text, truncated, and nothing else. The exit code lives in response_header() ("Process exited with code N"), which goes to the model, not to the hook. So in 0.152.0 the hook payload carries no exit status for shell commands at all; a silently failing command (false) is indistinguishable from a successful one.

What can be done, and what the spec's row should say: treat the string response the way the category classifier already treats error text. If the output matches one of the failure patterns (not_found, permission, syntax, wrong_command, build_failure, test_failure, timeout), write the failure event with that category; otherwise write nothing. Keep the object branch for MCP tools, whose response is the result JSON and can carry an error. Rewrite the two test cases with string payloads (one with "command not found" in it, one with "ok"). Update the README to state the fact plainly: shell tool_response is output text without an exit code, so Codex failure capture is heuristic and misses silent failures. That last sentence belongs in docs/agent-signaling.md too.

2. Group order in UserPromptSubmit breaks the already-trusted capture hook until you accept the review

Codex trusts a handler by its position key (path:user_prompt_submit:1:0) and a hash of its command; your file has the capture group trusted at index 1 today. The new map puts the status group first and the capture group second, so index 1 now holds a different command (hash mismatch, untrusted) and the capture group moves to index 2 (new key, untrusted). Between the first spawn after this change and your acceptance of the review, neither runs, and resume_id capture, which worked before, stops. Putting the capture group first in UserPromptSubmit keeps index 1 identical, so it stays trusted and only the new groups wait for review. Order within an event does not matter to either group. One-line change in buildCodexHooksMap, plus the corresponding expectation in TestCodexSetupHooks_InstallsTheClaudeShapedMap.
