Chat Storage Spec Coherence Check

Target: docs/specs/chat-storage-cleanup.md · Date: 2026-10-14

Verdict

2 issues found. The overall design is coherent with the observed storage layout and current Dispose/Restart flow, but the budget path can violate the grace rule, and the API response depends on cleanup result state that the spec does not define.

Findings

1. Budget eviction can bypass the one-hour grace period

Severity: high. The spec says the grace period is a correctness guard that lets Restart dispose, then copy the old transcript into the new session without a race. It also says a retention_days: 0 directory becomes eligible only after one hour.

The conflict is in the cleaner algorithm: age deletion applies grace + retention_days, but budget deletion says to delete remaining unreferenced candidates oldest-first without requiring them to be older than grace. A newly disposed transcript could therefore be deleted by the budget pass before Restart seeds the new session.

Evidence: grace contract at docs/specs/chat-storage-cleanup.md:113-121; age rule at docs/specs/chat-storage-cleanup.md:167-169; unrestricted budget wording at docs/specs/chat-storage-cleanup.md:170-172; test only explicitly protects grace for age deletion at docs/specs/chat-storage-cleanup.md:292-297.

Required correction: budget eviction may consider only unreferenced candidates that have passed the grace period. Add a test where storage is over budget and the only reclaimable directory is inside grace; it must remain.

2. Last-cleanup API data has no defined owner or persistence behavior

Severity: medium. The cleaner is required only to record a structured log entry. The API then returns a structured last_cleanup object with counts, byte totals, timestamp, and error count.

The spec says usage metrics may be cached, but does not say where the last-cleanup result is stored, whether it survives daemon restart, or how the endpoint obtains it from a log. This leaves two valid but different implementations: parsed logs versus in-memory cache.

Evidence: log-only cleaner telemetry at docs/specs/chat-storage-cleanup.md:174-179; API object at docs/specs/chat-storage-cleanup.md:249-255; underspecified cache language at docs/specs/chat-storage-cleanup.md:259-261.

Required correction: define a single authoritative cleanup-result cache, its initial null state, and its replacement on each completed pass. If it is deliberately ephemeral, state that daemon startup clears last_cleanup until the startup scan finishes; otherwise define a persisted status file.

Checks That Passed

  • Pass: Dispose-time transport cleanup is consistent with the existing chat bridge file roles and with keeping conversation.jsonl as the durable transcript.
  • Pass: The proposed cleanup point is after the current state removal and save sequence, so failed state operations can retain transport files.
  • Pass: Transcript deletion is periodic rather than synchronous in Dispose, preserving the existing Restart seed operation.
  • Pass: Skipping every session ID in state is a conservative active-session rule and does not depend on status interpretation.
  • Pass: The configuration shape, generated-contract requirement, Advanced UI placement, API documentation requirement, and focused backend/frontend tests cover the main implementation surfaces.
