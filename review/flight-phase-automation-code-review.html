Both findings corrected. Invalid stop decisions are rejected before changing the active stop. Non-increasing phase-entry timestamps persist an uncertain boundary that cannot bind automatic decisions. The findings and probe output below describe the pre-fix implementation.

Original findings (corrected)

1. An unplaceable stop clears an active stop — P1

Evidence: internal/flights/pilot.go:478–488, internal/flights/model.go:213–219, and the advance gate at internal/flights/pilot.go:333.

What this is
The current pilot stop is the block on automatic advancement until the user changes phase.
Problem
recordPilotStop unconditionally replaces f.PilotStop. A turn with no trusted phase visit is accepted and stored with pilotStopNoVisit; HasCurrentPilotStop then returns false. Starting with a valid active stop, sending an unplaceable stop, then a valid advance starts the executor. A stale stop can likewise replace a current stop with a different visit. This is more than ignoring an invalid stop: it removes an existing block.
Fix
Validate the stop's nonzero, current phase visit before replacing the active stop. Retain a visible error for stale or ambiguous decisions and leave the active stop intact. Add a regression covering valid stop → unplaceable/stale stop → advance, asserting no new session.
If left unchanged
A flight that the pilot stopped can resume automatically without a human override.
TestReviewProbeInvalidStopClearsBlock:
stop before=true; stop after unplaceable decision=false;
next advance phase=executing status=skipped

The probe used newDecisionExchange(StatePlanning), a normal stop decision, respondTurn with a zero start timestamp, and a normal advance decision. “Skipped” is the monitor's normal status for a processed pilot turn without classifier work; the observed flight state was executing.

2. A backward clock change makes an old turn eligible in a later phase visit — P2

Evidence: internal/flights/manager.go:329–335 and internal/flights/model.go:227–237. The implementation plan's Task 1 explicitly requires ambiguous phase boundaries to remain unusable for automation.

What this is
Phase visits prevent an old pilot decision from advancing work after the user changes the flight's stage.
Problem
setWorkflowState accepts a timestamp earlier than the previous boundary. Once the clock catches up, a delayed turn from the prior visit passes both timestamp comparisons and is assigned to the current visit. The visit counter does not help because the turn receives the wrong counter during retention.
Fix
Make non-increasing or otherwise ambiguous phase boundaries ineligible for automatic decisions, preserving enough ordering evidence to avoid assigning an old turn to a newer visit. Add a fake-clock regression for a turn started before an away-and-back stage edit, retained after a backward clock adjustment and recovery. Do not manufacture a timestamp that claims the ordering is known.
If left unchanged
A stale advance decision can start a worker in a later visit instead of being rejected. 
TestReviewProbeClockRollbackRebindsOldTurn:
turn began in visit=2; after backward clock and stage return,
bound visit=4 current=4

Concrete sequence: visit 2 starts at 12:00:00; the old turn starts at 12:00:01; after the clock moves back, stage edits enter executing at 11:59:58 and return to planning at 11:59:59; the turn is retained at 12:00:02. The current code binds it to visit 4.
