Flight phase automation — implementation review

Branch feature/flight-name-generator · 2026-10-28 · plan docs/superpowers/plans/2026-10-28-flight-phase-automation.md

What changed

The pilot now advances the flight itself: planning → executing and executing → reviewing. The decision is explicit in the pilot's own completed turn ({"advance":"executing"} / {"advance":"reviewing"}), and the daemon applies it under the flight's own lock, so a manual click and a pilot decision that race produce one session, not two.

Takeoff and completion stay the user's actions. The completion action is now presented as Review and commit, and it is the flight's single human review-and-commit checkpoint. The manual phase actions stay available as overrides; they now carry copy that says the pilot normally advances those phases.

A pilot turn is bound to the phase visit it began in — decided by the harness's own turn-start boundary, not by whichever phase happens to be current when the turn is retained — so a decision made before a stage edit cannot advance the phase after it, and a pilot stop applies to the visit it was recorded in. Every automatic transition records the deciding turn on its operation before the session is spawned, so a replay, a restart, or a manual return to an earlier phase starts nothing.

What the dashboard shows

Source-turn references

An automatic operation names the pilot turn that decided it, in the flight’s own snapshot and in the API payload (operations[].source_turn_id). The turn is a retained monitor turn with its own id, so the story links the two. In the scenario above the deciding turn is turn-flight-ws-pilot-7; in the Go tests it is the monitor turn id of the pilot turn that carried the decision, for example turn-sess-1-102.

When the pilot’s session is restarted, the turn is renamed with it, and the operation and the stop follow the new name — the visit and the start evidence stay where they were. That is TestRestartPreservesAdvanceProvenance.

Live-test limits

Live acceptance is pending.

The screenshots above are real renders of the dashboard, captured from the Playwright scenario with the flight API and the /ws/dashboard snapshot delivered under test control. The scenario image has no chat harness: it cannot run a pilot that decides to advance a phase, and it cannot start real executor, reviewer, or committer sessions. The daemon’s own transitions and the pilot’s advance decisions are covered by the Go manager and pilot tests.

Not exercised here, and still to be checked on a real flight with both a Claude and a Codex working target: a live pilot making the two advance decisions against real planning and execution evidence; the user trying the change at the commit checkpoint; a repair after approval needing renewed approval through the chat; and a failure staying visible. Nothing in this review claims that a live model judges readiness correctly — the daemon applies the pilot’s explicit decision and never judges readiness itself.
